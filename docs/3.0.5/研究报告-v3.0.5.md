## 0. TL;DR 结论速览

1. **一颗已发布缺陷需要紧急通道裁决**：手动范围 ±0.05s 幂等 duplicate 返回会把前端整个工程对象替换成假对象（F1，双向独立复核确认）。触发场景恰是幂等设计要保护的日常操作（重复框选/双击/时间码重复提交）。**建议不待 3.0.5，按 3.0.4 smoke-fix 先例出补丁**——开放问题 Q1。
2. **两位用户对候选清单的共识高度收敛**：「有感」交集 = 纠错取消延迟（F4）、accept_high/clear 轨作用域化（S2）、英文 tooltip 类文案收口（P1）、aligned_main_text prompt 说明（P4）、副轨删除 toast 可撤销提示（P7）；「无感」交集 = InjectionKey 类型化、悬空 pending 物理清理、perf 环境例根修（全部 D 组技术债，维持登记不占主题）。
3. **翻译失败成本模型是自费用户的第一痛点**：1/34 批解析失败 = 全量零落盘 100% 重烧，且行级解析兜底无 translated_text 模式（Qwen/GLM/Ollama 高危）、失败后连「白烧了多少 token」都不可见。增量补译（S1）+ 失败账单（F2）+ 行级兜底（F3）是同一件事的三半——用户 A 的第一优先。
4. **keep 闭环「功能已通、信任未通」**：数据链求证全部成立（确认 keep 确实参与重跑计算、导出只认 confirmed delete），但关键确认文案藏在 hover title、invalidated_count 被前端丢弃、红蓝并存零解释——决定 2.x 占位块用户敢不敢迁移。用户 B 的第二优先。
5. **「按轨隔离」心智正被自家批量按钮打穿**：逐条 accept/reject 已 patch 化 + 按轨隔离，但「信任全部高置信度/清除全部」仍是 timeline 级无差别且批量不进 undo——修的不是功能缺口而是 3.0.4 刚建立的信任（S2，双人「有感」）。
6. **范围草案**（§8）：主项 = F2+F3+S1 翻译失败成本三件套、S2 批量审阅收口、F4 取消延迟对齐（+F1 若不入紧急通道）；顺带 = P 组文案/覆层/审阅打磨批（纯前端小面）；S4/S5/S6 与 D 组全部维持登记。规模估约 3.0.4 的一半，日历 6-9 天量级（待 SPEC 复核）。

## 2. 3.0.4 交付质量总评（两位用户共识）

- **交付质量最高段 = J6 副轨纠错闭环**（A）：门控守卫（置灰非仅样式）、轨徽、审阅来源轨标注、accept patch 化无全量刷新、undo 双层捕获——逐条流可靠性承诺全部兑现。
- **翻译 undo 三层一致成立**（A）：快照先行 + 千段单 patch（revision +1 有测试固化）+ 列表视图孤儿回落自动弹回主轨。
- **keep 数据闭环真实成立**（B）：确认 keep 确实从自动裁剪删除区间扣除（project_service.py:2888-2935）、陈旧 trim 剔除在位、导出只认 confirmed delete（export_service.py:599-608）。
- **smoke-fix 八项修复复查全部有效**（A/B）：仅余波毛边（进度 message 通道被丢弃、取消后 token 丢弃、取消英文红框），无复发。
- **J1 基线零回退**（B）：静音/智能删除/逐条审阅流与 3.0.3 行为一致。

结论：3.0.4 的「骨架」交付达标；3.0.5 的用户价值空间集中在**失败路径的残值回收、批量路径的作用域收口、新习惯（keep/副轨）的可感知收口**三类。

## 5. 延后设计（本版不入，但设计约束已可预写——供后续版本或专项裁决直接引用）

### 5.1 定稿译文滑动窗（S5 的核心难点）

- **约束**：纠错骨架在派发前预构建全部批 payload（llm_service.py:1013-1019），并发 5 下批 N+1 构建时批 N 未定稿——引入批间依赖即事实串行（约 5× 时延）。滑动窗与并发互斥是结构性的，不是参数问题。
- **延后设计形态**（用户 A 的用户侧需求已采集，R-A-05）：「质量模式」config 开关 = 串行派发 + 上一批定稿译文随下批 payload 携带；默认关。重点课程 overnight 跑，水课用并发。
- **重启条件**：术语一致性的真机负反馈出现（跨批术语翻译不一致被用户报告），或 S5 与增量补译（S1）合并设计时一并评估串行补译模式。
