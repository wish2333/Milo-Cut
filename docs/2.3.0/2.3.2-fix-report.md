# Milo-Cut v2.3.2 GUI 响应性能分析与修复报告

> **日期**: 2026-07-20
> **类型**: Performance Audit（报告先行，未实施修复）
> **严重级别**: P1 High（用户体验严重受损）
> **触发来源**: 用户反馈 "跳播是不卡了，但是整个 GUI 反应还是卡，包括但不限于停止播放时指针跳转、右键菜单、字幕编辑等（不停止播放更不必说）这些操作"
> **影响版本**: v2.3.1 及更早
> **影响模块**: 全前端响应式链路（`WorkspacePage.vue` + `useEdit.ts` + `useSegmentEdit.ts` + `Timeline.vue` + `TranscriptRow.vue` + `VideoControls.vue` + `SubtitleOverlay.vue`）
> **前置修复**: v2.3.1 Bug D 已完成跳剪播放主路径优化（共享 `useEditedPlayback` 控制器、deleteRanges 规范化、SegmentState Map 预计算、subtitleSegments 独立索引、drawSilenceOverlay 二分）
> **本版重点**: v2.3.1 解决了"持续播放主路径开销"，本版聚焦"用户交互路径开销"——wholesale 项目替换导致的级联失效是元凶

## 0. Executive Summary

v2.3.1 的优化把 RAF 主循环（每帧 60Hz 的 checkSkip + SegmentState 计算）压到了 O(log N)，跳剪播放本身不再卡顿。但用户在 v2.3.1 上反馈"GUI 整体反应还是卡"，包括暂停时指针跳转、右键菜单延迟、字幕编辑卡顿、播放时一切交互都迟钝——这些症状指向**跳剪主路径之外的另一个性能瓶颈**。

本轮审计确认根因是**单一的 wholesale 项目替换链**：

```
用户操作（编辑文本 / 改时间 / 确认 edit / merge / split / mark / batch）
  → 后端 @expose 方法返回 self._current.model_dump()  [整个 Project 序列化]
  → 前端 useEdit.* / useSegmentEdit.* 把 res.data 赋给 project.value
  → props.project 引用变化 → WorkspacePage 所有 computed 重算
    -> activeTimeline / segments / edits / mergedSegments (O(N log N) sort)
    -> deleteRanges / segmentStateMap (O(N×E)) / subtitleSegments / playheadSegmentId
  → 子组件（Timeline / WaveformEditor / SubtitleOverlay）接收新数组 props
    -> 子组件内 computed 又重算一次 segmentStateMap / subtitleSegments
  → v-for 渲染：1167 段重新求 v-memo 表达式，477 个 TranscriptRow 重新 patch 检查
```

每个用户操作（甚至单次按键）都触发这条链。用户基准项目（1167 segments + 989 edits）单次链路开销保守估计 50–200ms，远超 16ms 帧预算。叠加播放期间的 RAF 持续开销，用户感知就是"卡到不能用"。

| 问题 ID | 名称 | 严重度 | 类型 | 是否在主路径 |
|--------|------|--------|------|------------|
| **G1** | wholesale 项目替换链 | **P0 Critical** | 架构 | 是（每次交互） |
| **G2** | 字幕文本编辑无 debounce | **P0 Critical** | 实现缺陷 | 是（每次按键） |

| **G5** | SubtitleOverlay 独立 RAF + 接收 mergedSegments 触发重建 subtitleSegments | P1 High | 架构冗余 | 是 |
| **G6** | VideoControls 模板内 v-for 971 deleteRanges divs | P1 High | 模板 | 是（每次 currentTime 变化） |

## 1. 用户反馈与现象

### 1.1 原文

> 现在跳播是不卡了，但是整个 GUI 反应还是卡，包括但不限于停止播放时指针跳转、右键菜单、字幕编辑等（不停止播放更不必说）这些操作。

### 1.2 症状拆解

| 症状 | 用户感知 | 触发场景 | 推测根因（待验证） |
|------|---------|---------|------------------|
| 停止播放时指针跳转 | 暂停后波形/进度条指针位置短暂错乱后归位 | 点击暂停按钮 / Space 键 | 暂停触发 `<pause>` 事件 → `videoPaused.value = true` → `useEditedPlayback` 的 `watch([previewMode, paused], sync)` 触发 controller.stop()；同时最后一次 `timeupdate` / `seeked` 与 currentTime 计算的级联渲染竞争 |
| 右键菜单卡顿 | 右键后菜单弹出有明显延迟（>200ms） | 字幕行 / 波形块 / 时间轴 | 右键前若发生过任何 project 替换，TranscriptRow 整列表还在重渲；contextMenuManager 的 setTimeout(0) + 多个 document listener 注册路径较长 |
| 字幕编辑卡顿 | 输入字符后界面冻结 100–500ms | 字幕文本输入框打字 | **G2 核心热点**：每次按键触发 `update_segment_text` → 后端 `model_dump()` → 前端 wholesale 替换 → 整个响应式树重算 |
| 不停止播放更卡 | 播放时所有操作（点击、输入、右键）都明显迟钝 | 任何播放期间的用户交互 | 播放期间 RAF 持续运行（主路径开销）+ 任何交互叠加触发 wholesale 替换（G1）→ 双重开销 |

### 1.3 与 v2.3.1 修复的关系

v2.3.1 §4 修订后的性能指标体系（§4.7）明确指出："**严禁在阶段 6 之前改 wholesale 替换**：它是非主路径开销，过早优化会分散注意力"。

这个判断在 v2.3.1 阶段是正确的——v2.3.1 阶段 1–5 是 RAF 主循环（持续 60Hz），是用户感知"播放卡顿"的直接原因；wholesale 替换只在 task 完成时触发一次，相对低优先级。

**但本轮审计发现**：wholesale 替换不仅发生在 task 完成时，**字幕编辑 / 确认 / merge / split / mark / batch 等所有用户交互都触发它**。这意味着：

1. v2.3.1 §4.4 热点 8 "整项目 wholesale 替换"的评级（MEDIUM，**非主路径**）**部分错误**
2. 实际上 wholesale 替换在交互路径上是**持续触发**的，与 RAF 主路径同级
3. v2.3.1 §4.5 约束 6 "严禁在阶段 6 之前改 wholesale 替换"的禁令在 v2.3.2 应当解除

## 2. 根因分析：wholesale 项目替换链

### 2.1 后端：所有 @expose 写操作都返回 `model_dump()`

`main.py` 与 `core/project_service.py` 中所有变更操作的标准模式：

```python
# main.py:1554-1597 典型模式
@expose
def update_segment(self, segment_id: str, updates: dict) -> dict:
    return self._mark_dirty(self._project.update_segment(segment_id, updates))

# core/project_service.py:1318-1365
def mark_segments(self, segment_ids, action, status="pending") -> dict:
    # ... 修改 self._current
    return {"success": True, "data": self._current.model_dump()}  # <-- 整个 Project
```

**`self._current.model_dump()` 的开销**（Pydantic v2 递归序列化）：

| 数据 | 用户基准项目大小 | 序列化开销估计 |
|------|---------------|--------------|
| `media` | 1 个 MediaInfo（~10 字段） | <1ms |
| `timelines[0].transcript.segments` | **1167 Segment × 7 字段** | 5–15ms |
| `timelines[0].edits` | **989 EditDecision × 10 字段** | 5–15ms |
| `timelines[0].analysis` | 数百 AnalysisResult | 2–5ms |
| 完整 model_dump（含 JSON 序列化给桥） | — | **总计 15–40ms** |

每个写操作都付出这个代价，无论改动是 1 个字段还是整个项目。

### 2.2 前端：所有 composable 方法都做 `project.value = res.data`

`frontend/src/composables/useEdit.ts` 13 个方法中 **11 个**遵循同样的模式：

```typescript
// useEdit.ts:16-24 典型模式
async function updateSegmentText(segmentId: string, text: string): Promise<boolean> {
  const res = await call<Project>("update_segment_text", segmentId, text)
  if (res.success && res.data) {
    snapshot()
    project.value = res.data   // <-- 整个 Project 替换
    return true
  }
  return false
}
```

涉及的方法：`updateSegmentText` / `updateSegmentTime` / `mergeSegments` / `splitSegment` / `searchReplace` / `markSegments` / `confirmAllSuggestions` / `rejectAllSuggestions` / `deleteSegment` / `deleteSilenceSegments` / `deleteSubtitleTrimEdits` / `generateSubtitleKeepRanges`。

`useSegmentEdit.ts` 中的 `updateSegmentText`（line 188-196）、`toggleEditStatus`（line 200-225）也遵循同样模式，且 `toggleEditStatus` 还多了一次 `get_project()` 调用（见 §3 G3）。

### 2.3 前端级联：所有依赖 segments / edits 的 computed 重算

`WorkspacePage.vue` 接收 props.project，下游派生链：

```
props.project (新引用)
  → activeTimeline = computed(() => project.timelines.find(...))           // O(T) T=timelines 数
  → segments = computed(() => activeTimeline.transcript.segments)           // 新数组引用
  → edits = computed(() => activeTimeline.edits)                            // 新数组引用
  → duration = computed(() => project.media.duration)                       // 原始值，跳过
    ↓ 以下全部重算
  → mergedSegments = computed(() => [...segments].sort(...))                // O(N log N) + 新数组
  → silenceCount = computed(() => segments.filter(s => s.type==="silence").length)  // O(N)
  → subtitleCount = computed(() => segments.filter(s => s.type==="subtitle").length) // O(N)
  → deleteRanges = computed(() => edits.filter(...).map(...).sort(...))     // O(E log E)
  → active edit decisions 等
    ↓ 透传给子组件作为 props
    → <Timeline :segments="mergedSegments" :edits="edits" ...>
       → Timeline.segmentStateMap = computed(() => buildSegmentStateMap(segments, edits))  // O(N×E) = 1167×989 ≈ 1.15M 操作
       → Timeline.subtitleSegments = computed(() => buildSubtitleIndex(segments))          // O(N)
       → Timeline.playheadSegmentId = computed(...)                                         // O(log N)
       → v-for 1167 段 + 477 TranscriptRow 的 v-memo 表达式重新求值
    → <WaveformEditor :segments="mergedSegments" :edits="edits" ...>
       → SegmentBlocksLayer.segmentStateMap 又重算一次（O(N×E)）
       → SegmentBlocksLayer.visibleBlocks 重算
       → WaveformCanvas.silenceSegments 重算（filter + sort O(N log N)）
    → <SubtitleOverlay :segments="mergedSegments" ...>
       → SubtitleOverlay.subtitleSegments 又重算一次（filter + sort O(N log N)）
       → SubtitleOverlay 独立 RAF 循环继续运行
    → <VideoControls :delete-ranges="deleteRanges" :current-time="currentTime" ...>
       → 模板内 v-for 971 deleteRanges divs 全部重新求值
```

### 2.4 单次操作总开销估算

以"用户在字幕编辑框打一个字符"为例，触发 `updateSegmentText`：

| 阶段 | 操作 | 估算耗时 |
|------|------|---------|
| 1 | 网络往返（pywebview 桥 + Python 调用） | 5–15ms |
| 2 | 后端 `update_segment_text` 修改 + `model_dump()` | 15–40ms |
| 3 | 后端 JSON 序列化 + 桥传输 | 5–15ms（200–500KB JSON） |
| 4 | 前端 `project.value = res.data` 触发 reactive | <1ms |
| 5 | WorkspacePage 级联 computed 重算（mergedSegments + deleteRanges + stateMap 等） | 10–30ms |
| 6 | Timeline 子组件 props 变化 + segmentStateMap 重算 | 30–80ms |
| 7 | SegmentBlocksLayer segmentStateMap 重算（第二次） | 30–80ms |
| 8 | SubtitleOverlay subtitleSegments 重算 | 5–15ms |
| 9 | VideoControls 模板 v-for 971 divs 求值 | 5–15ms |
| 10 | Vue flush + DOM patch | 5–20ms |
| **合计** | | **110–310ms per keystroke** |

用户感知：每个字符输入后界面冻结 100–300ms。打字速度被限制到 3–10 字符/秒。这就是"字幕编辑卡顿"的精确量化。

## 3. 性能热点清单（按严重度排序）

### G1: wholesale 项目替换链（CRITICAL，主路径）

**根因**：见 §2。

**关键文件:行**：

| 文件 | 行 | 问题代码 |
|------|----|---------|
| `main.py` | 1426-1430 | `get_project` 返回 `self._project.current.model_dump()` |
| `main.py` | 1554-1597 | 12 个 @expose 写方法都返回 `model_dump()` |
| `core/project_service.py` | 1318-1365 | `mark_segments` 等 8 个 service 方法返回 `model_dump()` |
| `frontend/src/composables/useEdit.ts` | 16-170 | 11 个方法都 `project.value = res.data` |
| `frontend/src/composables/useSegmentEdit.ts` | 188-225 | `updateSegmentText` / `toggleEditStatus` 都 wholesale |

**修复方向**（详见 §5 实施顺序）：

- **方案 A（彻底）**：后端返回 diff（仅变更的 segment / edit / 增量计数），前端按字段合并；引入 `ProjectPatch` 类型
- **方案 B（折中）**：后端继续返回 `model_dump()`，前端 `shallowRef` + 配套 `triggerRef`；子组件用 `watchEffect` 显式订阅自己关心的字段
- **方案 C（最小）**：只对高频操作（updateSegmentText / updateSegmentTime / toggleEditStatus）返回局部 patch，其他保持 wholesale

推荐方案 C 作为 v2.3.2 第一阶段，方案 A 作为 v2.4.0 的彻底重构。

### G2: 字幕文本编辑无 debounce（CRITICAL，主路径，按键级）

**文件:行**: `frontend/src/composables/useSegmentEdit.ts:188-196`

```typescript
async function updateSegmentText(segmentId: string, text: string): Promise<boolean> {
  if (onBeforeProjectUpdate && project.value) onBeforeProjectUpdate(project.value)
  const res = await call<Project>("update_segment_text", segmentId, text)
  if (res.success && res.data) {
    onProjectUpdate(res.data)   // 每次按键都 wholesale 替换
    return true
  }
  return false
}
```

对比 `updateSegmentTime`（同文件 line 156-184）已有 300ms debounce：

```typescript
function updateSegmentTime(segmentId, field, value) {
  // ...
  const timer = setTimeout(() => {
    pendingMap.delete(key)
    callback()  // 300ms 内只触发一次后端调用
  }, DEBOUNCE_MS)
  pendingMap.set(key, { timer, callback })
}
```

**关键差异**：

| 操作 | debounce | 单次开销 | 用户感知 |
|------|---------|---------|---------|
| 拖动字幕边缘改时间 | 300ms | 110–310ms | 流畅（拖动停止后才触发一次） |
| 输入字幕文本 | **无** | 110–310ms × N 字符 | 卡顿（每字符都冻结） |

**修复**：让 `updateSegmentText` 也用同样的 debounce 模式，本地维护 optimistic 文本，300ms 后才调用后端。

### G3: toggleEditStatus 双重 wholesale（HIGH，每次确认/拒绝）

**文件:行**: `frontend/src/composables/useSegmentEdit.ts:200-225`

```typescript
async function toggleEditStatus(segment, nextStatus?) {
  // ...
  if (state.activeEdit) {
    await call<Project>("update_edit_decision", state.activeEdit.id, status)
    // ↑ 后端已经返回了更新后的 Project，但前端丢弃了返回值
  } else if (state.displayStatus === "rejected") {
    const rejectedEdit = getEditForSegment(edits, segment)
    if (rejectedEdit) {
      await call<Project>("update_edit_decision", rejectedEdit.id, "confirmed")
      // ↑ 同上，返回值丢弃
    }
  } else {
    await call("mark_segments", [segment.id], "delete", "confirmed")
  }

  const projRes = await call<Project>("get_project")  // ← 第二次 wholesale 拉取！
  if (projRes.success && projRes.data) {
    onProjectUpdate(projRes.data)
  }
}
```

每次"点击确认/拒绝"图标都触发**两次**网络往返 + **两次**后端 model_dump + **一次**前端 wholesale 替换。

**修复**：使用 `update_edit_decision` / `mark_segments` 的返回值，去掉额外的 `get_project()` 调用。

### G4: mergedSegments 全量排序 + 数组重建（HIGH，每次 segments 变化）

**文件:行**: `frontend/src/pages/WorkspacePage.vue:390-392`

```typescript
const mergedSegments = computed<Segment[]>(() => {
  return [...segments.value].sort((a, b) => a.start - b.start)
})
```

**问题**：

1. **数组复制 + 排序**：1167 段 O(N log N) ≈ 12000 次比较 + 新数组分配
2. **触发下游新 props**：mergedSegments 是新数组引用，所有接收它的子组件（Timeline、WaveformEditor、SubtitleOverlay）都视为 props 变化，触发它们内部依赖 segments 的 computed 重算

**为什么是冗余的**：后端 `core/project_service.py` 在每次修改后已经保证 segments 按 start 升序（写入路径 `add_segments` / `update_segment` 都维护顺序），前端防御性排序在 99% 情况下不改变任何东西，但每次都付出 O(N log N) + 新数组的代价。

**修复方向**：

- 方案 A（推荐）：直接用 `segments`（已排序），移除 mergedSegments
- 方案 B：在 WorkspacePage 用一个 ref 缓存"上次 segments 引用 + 排序结果"，只在 segments 真的变化时重排（但 segments 已经按引用变化触发 computed，缓存意义不大）

如果担心后端排序不可靠，可在后端 service 层加一个 invariant assert（开发模式）。

### G5: SubtitleOverlay 独立 RAF + 接收 mergedSegments 触发重建（HIGH）

**文件:行**: `frontend/src/components/workspace/SubtitleOverlay.vue:14-53`

```vue
<script setup lang="ts">
const subtitleSegments = computed(() => buildSubtitleIndex(props.segments))

function findCurrentSubtitle(time: number): string {
  return findSubtitleAtTime(subtitleSegments.value, time)?.text ?? ""
}

function tick() {
  if (!props.videoRef) return
  currentText.value = findCurrentSubtitle(props.videoRef.currentTime)
  rafId = requestAnimationFrame(tick)
}
// ...startTracking / stopTracking 控制 RAF
</script>
```

**两个问题**：

1. **独立 RAF 循环**：SubtitleOverlay 有自己的 60Hz RAF，没和 `useEditedPlayback` 共享。`useEditedPlayback` 内部 `animationLoop` 已经每帧 publish currentTime 给 `onTimeUpdate` 回调，WorkspacePage 已经更新了 `currentTime.value`。SubtitleOverlay 完全可以订阅 `currentTime` 而不是自己跑 RAF。
2. **接收 `mergedSegments`**：WorkspacePage 模板 line 1999 `<SubtitleOverlay :segments="mergedSegments" ...>`，每次 wholesale 替换都触发 `buildSubtitleIndex`（filter + sort 1167 段）重算。

**修复**：

- 共享 currentTime（通过 props 或 inject）替代独立 RAF
- 改接收 `segments`（已排序）而不是 `mergedSegments`，且 `buildSubtitleIndex` 自身应基于 segment.id 引用稳定性做缓存（在 `props.segments` 引用未变时直接返回旧结果）

### G6: VideoControls 模板内 v-for 971 deleteRanges divs（HIGH，每次 currentTime 变化）

**文件:行**: `frontend/src/components/workspace/VideoControls.vue:225-235`

```vue
<template v-if="previewMode === 'edited' && deleteRanges?.length">
  <div
    v-for="(range, i) in deleteRanges"
    :key="i"
    class="absolute top-0 h-full bg-red-500/30"
    :style="{
      left: duration > 0 ? (range.start / duration) * 100 + '%' : '0%',
      width: duration > 0 ? ((range.end - range.start) / duration) * 100 + '%' : '0%',
    }"
  />
</template>
```

**问题**：

1. **971 个 div**：用户基准项目 971 个 deleteRanges，每个都绝对定位 + 计算 left/width
2. **被 progressPercent 触发**：模板外层 `<div :style="{ width: progressPercent + '%' }" />`（line 220-223）依赖 `progressPercent` computed（依赖 `currentTime`），**每次 currentTime 变化整个模板重新求值**，包括 971 个 deleteRanges div 的 v-for 表达式
3. **`:key="i"` 用索引**：如果 deleteRanges 顺序/数量变化，所有 div 都重新创建（不是复用）

**修复方向**：

- 把 deleteRanges 渲染拆到独立子组件，用 `v-once` 或独立 `v-memo="[deleteRanges]"` 隔离 currentTime 触发
- 或用 `<canvas>` 绘制 deleteRanges overlay（一次性绘制，只在 deleteRanges 变化时重绘）

## 4. 关键设计约束

实施任何修复前必须遵守以下 5 条约束，否则会引入新 bug。

### 约束 1：wholesale 替换的修复必须保持 undo/redo 历史完整

`useEdit.ts` 的每个方法都先调用 `snapshot()`（通过 `onBeforeProjectUpdate` 回调）把当前 project 推入 undo 栈，然后才发起后端调用。改用 diff patch 时，**undo 栈仍然保存完整 project 快照**（不能改成 diff 栈，否则单步 undo 还原不完整）。

### 约束 2：乐观更新必须可回滚

`useSegmentEdit.updateSegmentTime` 的乐观更新模式：

```typescript
const optimistic = replaceSegment(prev, segmentId, { [field]: value })
onProjectUpdate(optimistic)  // 立即更新 UI
// ... 后端调用，失败时 onProjectUpdate(prev) 回滚
```

改 debounce 时必须保留这个回滚路径。如果文本编辑加 debounce，乐观更新仍应立即生效，只是后端调用被延迟。

### 约束 3：SubtitleOverlay 共享 currentTime 时不能引入 RAF 同步问题

`useEditedPlayback` 的 RAF 由 `@play` / `@pause` 控制。如果 SubtitleOverlay 改用 props.currentTime 而不是独立 RAF + 直接读 `videoRef.currentTime`，要确保：

- currentTime 在 RAF 帧内更新（已经在 useEditedPlayback.animationLoop 内做）
- SubtitleOverlay 在 `previewMode === "original"` 时也工作（不依赖 deleteRanges）

### 约束 4：v-memo 不能漏掉任何影响行渲染的状态

G7 修复时，如果引入 `renderedRows` computed 把 `getSegmentState(seg)` 提前算好，**v-memo 表达式必须包含所有原始依赖**：

- `seg`（segment 引用）
- `state.displayStatus`
- `state.styleClass`
- `selectedSegmentIds.has(seg.id)`
- `selectedSegmentId === seg.id`
- `seg.id === playheadSegmentId`
- `seg.id === highlightedSegmentId`
- `globalEditMode`
- `selectionMode`

漏掉任何一个会导致 UI 不更新。

### 约束 5：后端 diff 返回格式必须向后兼容

如果引入 `ProjectPatch` 类型，必须：

- 旧前端（无 patch 处理逻辑）收到 patch 时降级为 `get_project()` 拉取完整项目
- 新前端收到完整 Project 时正常处理（向后兼容）
- patch 格式必须是 JSON 可序列化（Pydantic model_dump 兼容）
