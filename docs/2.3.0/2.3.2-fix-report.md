# Milo-Cut v2.3.2 GUI 响应性能分析与修复报告

> **日期**: 2026-07-20
> **修订**: v2（基于代码复核后的性能审计）
> **类型**: Performance Audit（报告先行，未实施修复）
> **影响版本**: v2.3.1 及更早
> **触发来源**: 用户反馈“跳播是不卡了，但是整个 GUI 反应还是卡，包括但不限于停止播放时指针跳转、右键菜单、字幕编辑等（不停止播放更不必说）这些操作”

---

## 0. Executive Summary

v2.3.1 已降低跳剪播放主循环的持续开销，但当前编辑交互仍可能触发整项目状态替换：后端写操作普遍返回 `self._current.model_dump()`，前端再把完整 `Project` 写入 `project.value`。这会使 `segments`、`edits` 及其下游派生数据失去引用稳定性，并可能重新触发 Timeline、Waveform 和字幕覆盖层的计算。

这个架构问题是真实存在的，但本报告此前把若干“可能发生的级联计算”直接写成了已测量的耗时，且误判了字幕文本编辑路径。当前 `TranscriptRow` 使用本地 `v-model`，只在 Enter、blur 或退出全局编辑模式时提交，不是每个字符调用后端。因此“110–310ms per keystroke”不能作为当前版本的事实结论。

本版结论：

1. G1 wholesale 替换链是主要的架构优化方向，但需要浏览器性能 trace 才能确定其在用户反馈中的占比。
2. G3 `toggleEditStatus` 的重复请求已由代码直接证实，是最高 ROI、低风险的立即修复项。
3. G4/G13 移除 `mergedSegments` 的前提不成立：`update_segment()` 当前不会保证时间排序，不能直接删除防御性排序。
4. G6 独立拆分 delete-range overlay 有较高收益；暂不建议立即改成 canvas。
5. G2 应改写为“文本提交路径的单次 wholesale 更新”，而不是“按键级 debounce”。

当前仓库验证结果：前端测试 **184/184 通过**，后端测试 **412/412 通过**。仓库中没有报告所引用的 `data/projects/20260720-八仙长评/project.json` 基准项目，因此 1167 segments / 989 edits 相关数值仍需外部数据或可提交的合成 fixture 验证。

## 1. 用户反馈与现象

### 1.1 症状拆解

| 症状 | 当前可支持的解释 | 仍需验证的部分 |
|---|---|---|
| 暂停后指针跳转 | `pause`、`timeupdate`、`seeked` 与响应式更新可能在相邻事件中竞争 | 是否存在可见错位，以及耗时来自哪里 |
| 右键菜单延迟 | 若此前发生项目替换，列表及相关子树可能正在 flush | 菜单本身的 `setTimeout(0)` 是否是主要耗时 |
| 字幕编辑提交卡顿 | blur/Enter 提交会触发一次完整项目替换 | 当前提交耗时及 Vue flush 耗时 |
| 播放期间更卡 | 播放 RAF 与交互触发的计算叠加 | 是否达到 long task 或掉帧阈值 |

### 1.2 字幕编辑路径的修正

当前实际路径是：

```
TranscriptRow 本地 editText
  → Enter / blur / 退出全局编辑模式
  → emit update-text
  → useSegmentEdit.updateSegmentText()
  → update_segment_text 一次桥接请求
  → 返回完整 Project
  → onProjectUpdate() 替换父级 project
```

`TranscriptRow.vue` 没有通过 `@input` 提交后端；`saveEdit()` 只在编辑提交时 emit。因此本报告不再把 G2 描述为“每字符后端请求”。

全局编辑模式仍需单独关注：关闭模式时，多个已修改行可能分别提交，形成短时间内的多次完整项目替换。这应通过组合式测试和浏览器 trace 验证，而不是假定为每键触发。

## 2. 根因分析：完整项目替换链

### 2.1 后端序列化与桥接传输

当前多个编辑 service 方法最终返回：

```python
return {"success": True, "data": self._current.model_dump()}
```

这会产生完整 `Project` 的 Python 序列化结果，并由 pywebview bridge 继续传输到前端。该模式在 `update_segment_text`、`update_segment`、`mark_segments`、`update_edit_decision` 等写操作中存在。

报告此前给出的 15–40ms 序列化估算没有实测依据，应改为“待测成本”。真实成本至少应拆成：

1. Python `model_dump()`；
2. bridge 返回值编码与传输；
3. 前端对象创建及响应式包装；
4. Vue 依赖重新读取与 DOM patch。

### 2.2 前端引用替换

`WorkspacePage` 将完整返回值通过 `project-updated` 传递到 `App.vue`，最终替换根级 `project` 引用。这样会使 `activeTimeline`、`segments`、`edits` 等 computed 的依赖失效。

需要注意：Vue computed 是惰性的，不是所有 computed 在引用变化时都立即执行。报告中的“全部 computed 重算”应理解为“在后续 render 或读取路径中可能重新计算”，具体耗时必须通过浏览器 trace 证明。

### 2.3 可信的高复杂度热点

`Timeline.vue` 与 `SegmentBlocksLayer.vue` 都会调用 `buildSegmentStateMap(segments, edits)`。当前 `resolveSegmentState()` 对每个 segment 遍历并筛选 edits，最坏复杂度接近 O(N×E)，并且两个组件各自构建一次。对 1167 segments / 989 edits，1.15M 级别的比较是合理的复杂度上界，但不是 30–80ms 的实测结论。

`mergedSegments` 还会复制并排序数组；`VideoControls` 在 currentTime 更新时会重新执行 delete-range 列表的模板表达式。这两项值得测量，但应避免把静态操作数直接等同于用户可感知耗时。

## 3. 性能热点与修复建议

### G1：wholesale Project 替换链（P1，架构问题）

**已确认事实**：后端写操作返回完整 Project，前端多个路径将其整体写入根级 project。

**影响**：可能造成下游数组引用变化、重复索引构建和大规模 render 检查。当前缺少性能 trace，因此暂不将其定为 P0 或直接断言为唯一元凶。

**修复建议**：

- v2.3.2：对高频、低结构变化操作引入局部 patch，并在前端按 segment/edit ID 合并；不能只缩小后端响应而继续整体替换 `project.value`。
- v2.4.0：设计统一 `ProjectPatch` 协议，保留完整 Project fallback。
- undo/redo 继续保存完整快照，patch 只用于当前状态更新，不替代历史快照。

### G2：文本提交路径无 debounce（P2，原结论修正）

当前文本输入本身是本地状态，后端只在提交时调用。因此不能以“每个字符冻结”为依据要求按键级 debounce。

仍可考虑：

- 在提交阶段使用局部 optimistic patch，避免提交后整项目替换；
- 对全局编辑模式关闭时的多个修改进行批量提交或单请求提交；
- 如果未来改为输入即保存，再引入 debounce，但必须有 flush、回滚和请求序列号。

### G3：`toggleEditStatus` 双重请求（P1，立即修复）

当前代码先调用 `update_edit_decision` 或 `mark_segments`，丢弃返回的完整 Project，随后再次调用 `get_project()`。这会产生两次 bridge 往返和两次完整序列化。

**修复**：直接消费第一次调用的返回值；失败时保留错误处理，只有返回格式不完整或协议不兼容时才 fallback 到 `get_project()`。

**验收**：一次 toggle 只允许一次编辑写请求；前端状态应使用该请求返回的 Project 更新。

### G4：`mergedSegments` 全量排序（P1，有条件）

当前代码：

```typescript
const mergedSegments = computed(() =>
  [...segments.value].sort((a, b) => a.start - b.start)
)
```

复制和排序确实存在，但报告此前错误地声称后端所有写路径都保证排序。`core/project_service.py:update_segment()` 会保持 segment 原有数组位置；修改 start/end 后可能破坏时间顺序。split/merge 也主要保持原有顺序。

**修复前提**：先在 service 层统一建立排序 invariant，并为 add/update/split/merge/import 编写测试。只有 invariant 成立后，才可移除 `mergedSegments` 并让 Timeline、Waveform、SubtitleOverlay 直接接收已排序的 `segments`。

在 invariant 尚未建立前，直接删除排序属于潜在功能回归，不应作为 v2.3.2 的无条件修复。

### G5：SubtitleOverlay 独立 RAF（P2）

独立 RAF 和 `useEditedPlayback` 的时间更新存在重复，但当前字幕查找已经使用独立 subtitle index，单次查找是二分路径。该项可降低一个 RAF 循环，但不能单独解释暂停时卡顿。

**建议**：传入父级 `currentTime`，同时验证 original/edited、播放/暂停、手动 seek 四种状态。original 模式不能依赖 edited playback RAF，必须确认 native `timeupdate` 与 `seeked` 能更新字幕。

### G6：VideoControls delete-range overlay（P1，需基准确认）

当前模板会在 progress bar 内遍历全部 delete ranges。若基准确实有约 971 个 range，currentTime 更新时会反复执行这些动态 style 表达式。

**推荐顺序**：

1. 先拆成只接收 `deleteRanges` 和 `duration` 的独立子组件；
2. 使用稳定 key 和 `v-memo` 隔离 currentTime 更新；
3. 只有 trace 证明 DOM 列表仍是瓶颈时，再评估 SVG/canvas。

### G7：TranscriptRow 重复 Map 查询（P3）

当前重复调用的是 O(1) Map 查询，主要成本仍在 `buildSegmentStateMap()` 本身。可以合并每行的状态读取，但预计收益小于修复 state map 的索引构建。

### G8：deprecated 状态查询 wrapper（P3）

这些 wrapper 内部确实会重新执行 `resolveSegmentState()`，但当前生产代码搜索未发现 Timeline 模板调用它们；主要调用点是组合式内部和测试。因此不应再描述为“每次模板调用”。可在后续清理 API 时移除。

### G9–G12：低优先级项

G9 的 1167 次 `find` 只发生在低频 I/O 快捷键；G10/G11 属于窗口缩放和 popup 点击路径；G12 主要是嵌套滚动导致菜单意外关闭的 UX 问题。它们不应阻塞主性能修复。

## 4. 关键设计约束

1. **Undo/redo**：patch 更新不能替代完整快照；每次用户语义操作最多产生一个 undo 节点，不应因 debounce 或多个响应产生重复历史。
2. **乐观更新可回滚**：失败时恢复提交前状态；回滚不能覆盖用户随后产生的新修改。
3. **请求顺序**：旧请求可能晚于新请求返回。文本和时间更新必须使用 request sequence/revision，禁止旧响应覆盖新状态。
4. **关键操作先 flush**：seek、export、undo、redo、项目关闭和切换 timeline 前，必须 flush 待提交更新。
5. **patch 向后兼容**：旧前端收到 patch 时必须能 fallback 到 `get_project()`；新前端收到完整 Project 也必须正常工作。
6. **排序 invariant**：移除 `mergedSegments` 前，后端所有 segment 写路径必须保证按 start 升序，并有回归测试。
7. **字幕时间来源**：共享 currentTime 后，original/edited、播放/暂停和 seeked 都必须保持字幕显示正确。
8. **v-memo 完整性**：任何模板优化都不能遗漏 segment、状态、选择、playhead、highlight、编辑模式等影响渲染的依赖。

## 5. 修订后的实施顺序

### 阶段 0：建立可复现基线（必须先做）

| 任务 | 验收 |
|---|---|
| 提供脱敏真实项目或合成 fixture | 至少覆盖 1167 segments / 989 edits 规模 |
| 加入 Playwright trace | 覆盖暂停、右键、文本提交、toggle、播放期间操作 |
| 记录 bridge、Python、Vue flush、DOM patch 分段耗时 | 输出 p50/p95/p99，而非静态估算 |

### 阶段 1：低风险高 ROI

| 任务 | 目标 |
|---|---|
| G3 删除 `toggleEditStatus` 额外 `get_project()` | 每次 toggle 只保留一次写请求 |
| G6 拆分 delete-range overlay | currentTime 更新不重跑 range 列表 |
| 增加对应 Vitest 回归测试 | 验证调用次数、状态更新和 UI 依赖 |

### 阶段 2：局部更新协议

| 任务 | 目标 |
|---|---|
| 高频 segment/edit 操作返回 `ProjectPatch` | 减少序列化和桥接传输 |
| 前端按 ID 局部合并 | 保持未修改 segment/edit 的引用稳定 |
| 保留完整 Project fallback | 不破坏旧调用方和 undo/redo |
| 增加请求序列号 | 防止旧响应覆盖新状态 |

### 阶段 3：索引和派生数据优化

| 任务 | 前提 |
|---|---|
| 建立 edit → segment/interval 索引 | 先验证状态语义不变 |
| 复用 Timeline 与 Waveform 的 state map | 避免两个组件重复 O(N×E) 构建 |
| G5 共享 currentTime | 完成 original/edited/seek 回归测试 |
| G4/G13 移除 mergedSegments | 仅在排序 invariant 已落地后执行 |

### 阶段 4：v2.4.0 长期重构

- 完整 `ProjectPatch` 协议；
- 规范化的按 ID 状态存储或 selector；
- 评估虚拟滚动；
- 仅在 profiling 证明必要时评估 Worker/WASM。

## 6. 性能指标与测试方法

### 6.1 指标

| 指标 | 建议目标 | 说明 |
|---|---:|---|
| 普通文本输入 keydown → 下一帧 | p95 < 16ms | 测本地输入，不应包含后端提交 |
| 文本提交 → UI 稳定 | p95 < 100ms | 单独测 blur/Enter/全局编辑关闭 |
| toggle bridge 写请求数 | = 1 | 必须验证 G3 |
| toggle 完成时延 | 记录基线后再定目标 | 受 pywebview 和 Python 调度影响 |
| Project patch/替换后的 Vue flush | p95 < 50ms | 必须用真实 trace 校准 |
| currentTime 更新时 VideoControls patch | p95 < 4ms | 验证 G6 |
| 播放期间 long task | 0 个 >50ms | 观察交互期间帧阻塞 |
| 单次 seek 全链路 | p95 < 32ms | 包括事件、响应式和 DOM patch |

### 6.2 分层测试

| 层级 | 工具 | 必须覆盖 |
|---|---|---|
| L1 | Vitest | toggle 单请求、patch 合并、请求顺序、flush/rollback |
| L2 | Vitest + happy-dom | composable 与组件响应式更新 |
| L3 | Playwright trace | 暂停、seek、右键、文本提交、toggle、播放中操作 |
| L4 | PerformanceObserver / Chrome trace | long task、帧率、Vue flush、DOM patch |

当前已有测试全部通过，但尚未覆盖性能指标和 G3 单请求约束。

### 6.3 基准数据

报告原先引用：`data/projects/20260720-八仙长评/project.json`，1167 segments、989 edits、audio-only WAV。该文件当前不在仓库中，不能称为仓库内可复现基准。

落地前应选择以下一种方式：

1. 提交脱敏、可分发的基准 project fixture；或
2. 编写确定性的合成 fixture 生成器，并固定 segments/edits 分布；或
3. 在本地测试报告中明确标记外部数据来源和校验 hash。

## 7. 已知风险与未解决问题

| 风险 | 描述 | 缓解 |
|---|---|---|
| patch 与 undo 不一致 | 局部更新可能导致历史快照缺失 | 继续保存完整快照 |
| 旧响应覆盖新响应 | debounce 或并发请求返回顺序不确定 | revision/token 校验 |
| G4 删除排序回归 | 时间编辑后 segments 可能乱序 | service invariant + 测试 |
| G5 original 模式字幕失效 | edited playback 不一定持续 RAF | 同时覆盖 native timeupdate/seeked |
| G6 子组件拆分不完整 | 父级仍传递不稳定 props 会继续触发更新 | 只传稳定的 ranges/duration |
| patch 兼容性 | 旧前端无法识别新格式 | schema_version + 完整 Project fallback |
| 静态估算误导优先级 | 操作数不等于真实耗时 | 以 Playwright trace 为最终依据 |
