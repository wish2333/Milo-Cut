## 1. Bug A：audio-only 项目 OTIO / EDL / XML 导出空文件（P0 Critical）

### 1.1 现象

项目 `20260720-八仙长评`（音频 only 的 `.wav` 文件）点击导出 OTIO / EDL / Premiere XML 后，**只生成空文件**（EDL 仅含 TITLE/FCM 头、XML 仅含空 sequence、OTIO 仅含空 tracks），且接口返回 `success=True`，没有任何错误提示。

视频 / 音频文件本身的导出（`export_video` / `export_audio`）功能正常。

### 1.2 根因

`core/export_timeline.py:_build_keep_ranges` (line 615-641) 计算出 keep ranges 后，在末尾用一条"按帧数过滤零长区间"的语句清理浮点误差：

```python
# 修复前 (line 641)
return [(s, e) for s, e in keep_ranges if _sec_to_frames(e - s, fps) > 0]
```

其中 `_sec_to_frames`：

```python
def _sec_to_frames(seconds: float, fps: float) -> int:
    return int(round(seconds * fps))
```

**当 `fps = 0.0` 时（audio-only 媒体的合法值），`seconds * 0.0` 恒为 `0.0`，`int(round(0.0))` 恒为 `0`，`0 > 0` 恒为 `False`** — 所有 keep ranges 全部被过滤掉，三个导出函数拿到空数组继续生成"合法但无内容"的文件。

### 1.3 影响机制（数据流）

```
main.py:export_edl / export_otio / export_xmeml_premiere (line 1981-2033)
  -> project.media.model_dump()         # fps=0.0 for .wav
  -> core/export_timeline.py:export_edl(...)
       -> fps = media_info.get("fps", 25.0)    # 拿到 0.0 (默认 25.0 仅在 key 缺失时生效)
       -> _build_keep_ranges(segs, edits, dur, fps=0.0)
            -> 计算 keep_ranges = [(0, 34.5), (38.1, ...), ...]   # 正确
            -> line 641 过滤: _sec_to_frames(34.5, 0.0) = 0 > 0 = False
            -> 返回 []   <-- 全部清空
       -> 三个导出函数 for-loop 不进入，只写头/空骨架
       -> return {"success": True}   <-- 无错误！
```

### 1.4 为什么 `export_video` / `export_audio` 不受影响

视频 / 音频导出走的是 `core/export_service.py:_compute_keep_ranges` (line 681-702)，**该函数没有 fps 过滤**，无条件返回全部 keep ranges。这就是用户感知"视频导出正常、timeline 导出空文件"的根因。

### 1.5 为什么只有"八仙长评"受影响

这是用户的**第一个 audio-only 项目**。任何视频文件（mp4 / mkv / mov）的 ffprobe 探测结果都必然 `fps > 0`，bug 永不触发。`core/ffmpeg_service.py:140-147` 在没有视频流时显式设置 `fps = 0.0` 是正确行为，问题出在下游消费者未处理这个边界。

### 1.6 修复方案

**修复 1（核心防御）**：`_build_keep_ranges` 加 `fps <= 0` 守卫，audio-only 媒体改用时长过滤：

```python
# core/export_timeline.py:640-648 (修复后)
# Filter out ranges that produce 0 frames (floating-point rounding edge cases).
# When fps<=0 (audio-only media: .wav/.mp3 probed with fps=0.0), _sec_to_frames
# always returns 0, which would silently eliminate ALL keep ranges and produce
# an empty timeline file (bug: EDL/XML/OTIO exports for audio-only projects).
# Fall back to a duration-only filter for audio-only media.
if fps > 0:
    return [(s, e) for s, e in keep_ranges if _sec_to_frames(e - s, fps) > 0]
return [(s, e) for s, e in keep_ranges if (e - s) > 0]
```

**修复 2（兜底防御）**：三个导出函数（`export_edl`、`_build_xmeml_core`、`export_otio`）入口处，若 `fps <= 0` 默认为 25.0（NLE timeline 标准 PAL 帧率），同时打 warning 日志：

```python
# 在 export_edl / _build_xmeml_core / export_otio 三处的 fps 取值后
fps = media_info.get("fps", 25.0)
if fps <= 0:
    logger.warning(
        "export_timeline: media_info.fps={} (audio-only?), defaulting to 25.0",
        fps,
    )
    fps = 25.0
```

兜底防御的目的是避免下游 `_seconds_to_timecode(seconds, fps)` 在 `fps=0` 时执行 `total_frames % int(fps)` 触发 `ZeroDivisionError`（虽然修复 1 让 keep ranges 非空后才会走到这里，但作为防御性措施仍然必要）。

## 2. Bug B：导出汇总摘要数据错误（P1 High）

### 2.1 现象

用户在导出页点击导出按钮后弹出的"导出汇总摘要"对话框（`EditSummaryModal`）显示的 **裁剪掉时长 / 占比 / 待删除条数** 与工作区右上角状态徽章显示的 `N edits | -M:S` **数值不一致**。右上角是对的，弹窗是错的。

### 2.2 根因

两个数据源用了不同的筛选条件：

| 显示位置 | 数据源 | 筛选条件 |
|---------|--------|---------|
| 右上角徽章 (`WorkspacePage.vue:1629`, `ExportPage.vue:382`) | 前端 `useExport.ts:confirmedEdits` | `e.status === "confirmed" && e.action === "delete"` |
| 弹窗摘要 (`EditSummaryModal.vue`，由 `ExportPage.vue:599` 渲染) | 后端 `core/project_service.py:get_edit_summary` | `e.action == "delete" and e.status in (EditStatus.PENDING, EditStatus.CONFIRMED)` |

后端的筛选条件**错误地把 `PENDING` 状态也算作"已确认删除"**，导致：

- `edit_count` 包含所有 pending delete（用户尚未决定）
- `delete_duration` 把 pending 区间全部累加
- `delete_percent` 因此虚高
- `warnings` 触发条件（>40% 总时长、>60s 单段、3+ 连续）也基于错误数据

### 2.3 影响证据

以用户项目 `20260720-八仙长评` 为例（修复前）：

```
后端 get_edit_summary (错误，把 pending 算入):
  edit_count     = 690 (silence confirmed) + 177 (subtitle_trim pending) + 67 (llm confirmed) + 37 (user confirmed) = 971
  delete_duration ≈ 1320 秒
  delete_percent ≈ 79% (>40% → 触发红色警告)

前端 confirmedEdits (正确，只看 confirmed):
  edit_count = 690 + 67 + 37 = 794
  delete_duration ≈ 685 秒
```

差距：约 177 条 edits、约 636 秒时长。**用户看到的两个数字差近一倍**。

### 2.4 修复方案

统一前后端语义 — 导出摘要只统计真正会被删除的 `CONFIRMED` edits：

```python
# core/project_service.py:1423-1435 (修复后)
# Compute delete duration
# IMPORTANT: only count CONFIRMED edits here. Earlier versions also included
# PENDING, which made the export summary modal show inflated edit_count /
# delete_duration / delete_percent compared to the top-right status badge
# (which uses frontend useExport.confirmedEdits == status=="confirmed").
# The two must stay in sync; otherwise users see contradictory numbers.
delete_duration = 0.0
confirmed_edits = [
    e for e in edits
    if e.action == "delete" and e.status == EditStatus.CONFIRMED
]
for edit in confirmed_edits:
    delete_duration += edit.end - edit.start
```

### 2.5 回归测试

新增 `tests/test_project_service.py::TestProjectService::test_get_edit_summary_excludes_pending`，覆盖三种状态：

1. 3 条 pending silence edits → summary 应报 `edit_count=0, delete_duration=0`
2. 确认第 1 条 → `edit_count=1, delete_duration=0.5`
3. 拒绝第 2 条、确认第 3 条 → `edit_count=2, delete_duration=2.5`（0.5 + 2.0）

## 3. Bug C：导出与标记完全不符（P1 High，已修复）

### 3.1 现象

用户在 edited 跳剪预览模式下看到某些片段被标记为"删除"（红色块、播放时自动跳过），但导出后的视频/音频文件中**这些片段原样保留了**。具体表现：

- 已标记删除的片段仍被导出
- 在 `subtitle_trim` 覆盖范围内的片段仍被导出

### 3.2 根因

`subtitle_trim` 类型的 edits 在创建时 `status` 固定为 `PENDING`，**永远不是 confirmed**。前端预览把 `source === "subtitle_trim"` 当作"隐式 confirmed"来跳剪，后端导出却只看 `status` 字段。

**前后端筛选条件差异表**：

| 位置 | 文件:行 | 筛选条件 | subtitle_trim 行为 |
|------|---------|----------|-------------------|
| 前端 confirmedEdits (右上角徽章、导出页统计) | `useExport.ts:26-28` | `e.status === "confirmed" && e.action === "delete"` | **排除** |
| 前端 deleteRanges (工作区跳剪) | `WorkspacePage.vue:194-196` | `e.action === "delete" && (e.status === "confirmed" \|\| e.source === "subtitle_trim")` | **包含** |
| 前端 deleteRanges (导出预览跳剪) | `PreviewPlayer.vue:30-32` | 同上 | **包含** |
| 后端 _get_confirmed_deletions (视频/音频/SRT/VTT) | `export_service.py:435-439` | `edit.get("action") == "delete" and edit.get("status") == "confirmed"` | **排除** |
| 后端 _build_keep_ranges (EDL/xmeml/OTIO) | `export_timeline.py:640-643` | `e.get("status") == "confirmed" and e.get("action") == "delete"` | **排除** |

**核心矛盾**：前端 2 处包含、后端 2 处排除。用户在预览中"看到跳过"≠ 导出时"真的删除"。

### 3.3 subtitle_trim 创建路径

```
core/project_service.py:2091 generate_subtitle_keep_ranges(padding=0.3)
  -> line 2142-2162: 遍历字幕间隙区间
  -> 创建 EditDecision(
       action="delete",
       source="subtitle_trim",     # line 2158
       status=EditStatus.PENDING,  # line 2159  <-- 关键
       target_type="range"
     )
  -> line 2164: _update_active_timeline(edits=existing_edits + new_edits)
```

### 3.4 影响证据（用户项目数据）

```
subtitle_trim 详情 (项目 20260720-八仙长评):
  数量: 177 条全部 PENDING
  总时长: 636.6 秒 (~10.6 分钟)

前端预览跳剪范围 (confirmed + subtitle_trim): 794 + 177 = 971 条
后端导出实际删除 (仅 confirmed):              794 条
差距:                                          177 条 / 636.6 秒
```

用户在预览模式下以为已经"删掉"了约 10.6 分钟的字幕间隙，导出后发现这些区间**全部保留**在最终视频里。这就是"导出与标记完全不符"的精确量化。

### 3.5 全部"已标记但导出时被忽略"的 edit 类型

| source | 创建时 status | 是否被导出忽略 | 是否合理 |
|--------|-------------|--------------|---------|
| `subtitle_trim` | PENDING | **是** | **不合理** — 前端预览已"跳剪"，用户感知是"已删" |
| `silence_detection` (如有 pending) | PENDING | 是 | 合理 — 前端未特殊处理，预览也不跳过 |
| `llm_smart` (13 条 rejected) | REJECTED | 是 | 合理 — rejected 本就不应删除 |

> 注：用户当前项目里 `silence_detection` 全部为 confirmed (690 条)，无 pending；但代码逻辑上若未来出现 pending 的 silence_detection，行为也是会被导出忽略，与前端预览一致。

### 3.6 历史背景

`docs/2.1.1/audit-report-2.1.1-7.md:159` 当时记录的判断：

> 导出侧 (`useExport.ts:28`) 审计确认导出过滤条件不应改动 — 导出应该只删除用户显式确认的区间，subtitle_trim 作为自动检测的待定项，除非用户确认否则不应进入导出删除集。这是**正确的当前行为**。

2.1.1 当时为了快速修复"工作区跳剪体验"问题，仅在 `WorkspacePage.vue:196` 和 `PreviewPlayer.vue:32` 加了 `source === "subtitle_trim"` 特判，**没有同步更新后端**。这就埋下了"预览/导出语义分裂"的雷，直到 v2.3.1 用户首次在大项目上对比两者才暴露。

### 3.7 修复方案（已实施：方案 A）

**采用方案 A**：让 `subtitle_trim` 创建时 `status=CONFIRMED`。

决策依据（来自用户）：
> subtitle_trim 创建肯定是立即 confirmed 的，也没有别的入口 confirmed，又是快速的工作随时可以删了重新检测的。

实施位置 `core/project_service.py:2153-2183`（`generate_subtitle_keep_ranges` 内 EditDecision 构造）：

```python
# 修复前
new_edits.append(EditDecision(
    ...
    source="subtitle_trim",
    status=EditStatus.PENDING,    # <-- 漏掉导出
    ...
))

# 修复后
new_edits.append(EditDecision(
    ...
    source="subtitle_trim",
    # v2.3.1: subtitle_trim is a fast, user-triggered utility (regenerable
    # on demand via delete_subtitle_trim_edits + generate_subtitle_keep_ranges).
    # Unlike LLM suggestions that need user review, subtitle_trim edits
    # represent deterministic inter-subtitle gaps the user has chosen to cut.
    # Mark CONFIRMED at creation so that:
    #   1. export_video/audio/srt/vtt apply them immediately
    #      (via _get_confirmed_deletions: action=delete & status=confirmed)
    #   2. export_timeline EDL/xmeml/OTIO apply them too
    #      (via _build_keep_ranges: same filter)
    #   3. frontend useExport.confirmedEdits counts them, so the top-right
    #      badge and export summary modal agree with the WorkspacePage /
    #      PreviewPlayer deleteRanges which already treated source=
    #      subtitle_trim as implicitly confirmed (since v2.1.1).
    status=EditStatus.CONFIRMED,
    ...
))
```

**为何不采用方案 B / C**：
- 方案 B（后端 `_get_confirmed_deletions` 加 source 特判）会让数据模型里"status=PENDING 但实际要删除"的歧义永久存在
- 方案 C（前端去掉 subtitle_trim 特判）会让预览变得更差，不推荐

**为什么方案 A 是正确的**：subtitle_trim 不是 LLM 建议需要审核，它代表"字幕之间的间隙"——这些区间没有任何字幕内容，是确定性的"该剪掉"区间，语义上等同于用户已经确认。`delete_subtitle_trim_edits` (line 1113) 提供了一键清除重新生成的入口，符合"快速工具"定位。

### 4.4 性能热点清单（按修订后严重度排序）

> 严重度按"是否在持续播放主路径 + 修复依赖关系"重新评级。原 v1 评级已弃用。

#### 热点 1：checkSkip() 在 RAF 循环内做 O(K) 线性扫描（CRITICAL，主路径）

**文件:行**: `WorkspacePage.vue:201-209` + `PreviewPlayer.vue:129-137`（两处相同）

```typescript
function checkSkip(time: number): boolean {
  for (const range of deleteRanges.value) {   // O(K) 线性扫描
    if (time >= range.start && time < range.end) {
      videoRef.value.currentTime = range.end  // 触发 <seeked> -> 级联
      return true
    }
  }
  return false
}
```

**影响**: 用户项目（已修复后）的删除区间数达 **971 条**（794 confirmed + 177 subtitle_trim）。checkSkip 每帧最多跑 971 次比较 × 60fps = **58260 次比较/秒**。每次命中触发的 `<seeked>` 事件会再次进入 checkSkip（见热点 9）。

#### 热点 3：v-memo 依赖 getSegmentState → 每行都重算（CRITICAL，主路径，v2 升级）

**文件:行**: `Timeline.vue:314`（v-memo 表达式）+ `Timeline.vue:151`（getSegmentState 在模板内被多次求值）

```vue
v-memo="[seg, getSegmentState(seg).displayStatus, ..., seg.id === playheadSegmentId, ...]"
```

**v1 错误判断**: "只有 2 行重渲"。
**v2 修正**: `v-memo` 减少的是**子树 patch**，但 `v-memo` 表达式本身**每帧每行都要算**。对 1000+ 行 TranscriptRow，每行调用 `getSegmentState(seg)` → `resolveSegmentState()` 内含 `edits.filter() + sort()`，总开销 = 行数 × edits 数 × log(edits)。1000 行 × 989 edits × ~10 = **约 10^7 次操作/帧**。

这才是和 checkSkip 同级的真热点，必须与跳剪控制器一起进入第一阶段。

#### 热点 9：handleVideoSeeked 重入 checkSkip 造成 seek 风暴（CRITICAL，主路径）

**文件:行**: `WorkspacePage.vue:221-228` + `PreviewPlayer.vue:177-184`（两处相同）

seek → seeked → checkSkip → 再 seek 链式跳转，相邻 / 部分重叠区间下可形成单帧多次 seek，用户感知为"指针乱跳"。

#### 热点 2：playheadSegmentId 每帧 O(N) 线性 find（HIGH，主路径）

**文件:行**: `Timeline.vue:151-155`

```typescript
const playheadSegmentId = computed<string | null>(() => {
  const t = props.currentTime ?? 0
  const seg = props.segments.find(
    s => s.type === "subtitle" && t >= s.start && t <= s.end
  )   // O(N)
  return seg?.id ?? null
})
```

**影响**: 1167 segments 每帧扫描。

#### 热点 4：visibleBlocks computed 每可见段调用 resolveSegmentState（HIGH，主路径）

**文件:行**: `SegmentBlocksLayer.vue:62-81`

视图跟随播放头滚动（200ms throttle）时触发。50 可见段 × 989 edits = 49450 次过滤操作 / throttle 周期。复用热点 3 的预计算 Map 可消除。

#### 热点 5：drawSilenceOverlay 每次重绘遍历全部 segments（MEDIUM，主路径）

**文件:行**: `WaveformCanvas.vue:138-155`

690 silence 段每次 viewStart 变化都全量遍历。修复方向：预筛选可视窗口、OffscreenCanvas 缓存静态层。

#### 热点 8：整项目 wholesale 替换（MEDIUM，**非主路径**，v2 降级）

**文件:行**: `useAnalysis.ts:38`、`project_service.py:819`、`main.py:183`

**v1 错误判断**: 列为 P1，与跳剪同级。
**v2 修正**: 它只在 task 完成（静音检测 / LLM / 字幕修正）时触发**一次**，不在持续播放主路径上。用户感知的"卡到不能用"是 RAF 主循环的持续开销，不是 task 完成时的单帧 spike。

修复方向应**后置**：先完成主路径优化（热点 1/2/3/4/9），用真实 Performance trace 判断 wholesale 替换是否仍是问题。注意 `shallowRef` 不是银弹，会导致嵌套字段更新不触发 UI，需要配套的 triggerRef 显式触发。

#### 热点 6：deleteRanges computed 在 edits 变化时全量重建（LOW，非主路径）

**文件:行**: `WorkspacePage.vue:194-199` + `PreviewPlayer.vue:30-35`

只在 edits 数组变化时触发，不在每帧。修复方向：后端按 start 有序返回 deletes；前端跳过 sort。

#### 热点 7：mergedSegments / silenceCount / subtitleCount 全量扫描（LOW，非主路径）

**文件:行**: `WorkspacePage.vue:413-418`

只在 project 变化时触发。修复方向：后端直接返回分项计数。

### 4.5 关键设计约束（v2 新增）

实施任何修复前必须遵守以下 6 条约束，否则会引入新 bug。

#### 约束 1：deleteRanges 必须先规范化再二分

普通二分查找无法正确处理**重叠 / 相邻**区间。例如 `[0-5], [3-8], [10-15]` 数组中查找 time=4，二分命中 `[3-8]` 后跳到 8，但 `[0-5]` 也覆盖 4，可能漏判。

**正确流程**：
1. 过滤无效区间（`end <= start`、`end < 0`）
2. 按 `start` 升序排序
3. **合并重叠或相邻区间**（合并阈值可配置，如 0.05s）
4. 对合并后的有序数组用二分查找或"当前区间游标"法

这等价于构造专用的 `playbackRanges: NormalizedRange[]`，由独立的 `normalizeDeleteRanges(raw): NormalizedRange[]` 纯函数负责。

#### 约束 2：seeking 状态机必须区分 4 种 seek 来源

简单的 `isSeeking: boolean` 锁会丢失上下文。应区分：

| seek 来源 | 行为 |
|---------|------|
| 用户主动 seek（点击进度条 / 方向键） | 立即响应，跳剪控制器应跳过当前帧的 checkSkip |
| 程序跳剪 seek（checkSkip 命中） | 必须屏蔽下一次 `<seeked>` 的重入 checkSkip，避免风暴 |
| 连续删除区间（seek 落点又在另一删除区间内） | 必须继续跳到下一个 keep range 起点，不能停在删除区间内 |
| seek 尚未完成时再次修改目标（用户在 seek 中又点进度条） | 必须作废旧目标，避免竞争 |

**推荐设计**: 维护 `skipTarget: { generation: number, target: number }` 代际 token。每次发起 seek 自增 generation；`<seeked>` 回调时检查 generation 是否匹配，不匹配则丢弃。

#### 约束 3：subtitleSegments 必须建立独立索引

借鉴 `SubtitleOverlay.vue:14-53` 的游标 / 二分前，必须先认识到**它当前实现是错的**：

```typescript
// SubtitleOverlay.vue:37-40 (现有缺陷)
if (s.type !== "subtitle") {
  lo = mid + 1   // 中点是 silence 时直接向右
  continue
}
```

混合 subtitle / silence 数组中，silence 可能任意位置插入，二分会跳过左侧合法 subtitle。**正确做法**：

1. 用 `computed(() => segments.value.filter(s => s.type === "subtitle").sort(...))` 建立纯 subtitle 索引
2. 游标 / 二分只在这个索引上操作
3. 游标必须处理：倒退 seek（重置游标）、随机 seek（二分重定位）、segments 变更（重置游标，已有 watch）

#### 约束 4：SegmentState Map 必须保留 resolveSegmentState 全部语义

预计算 `Map<segmentId, SegmentState>` 时，不能只按 `target_id` 建索引。`resolveSegmentState()`（`segmentHelpers.ts:23-56`）的完整语义包括：

- `target_id` 精确匹配
- 时间 overlap 匹配（`isOverlapping(e, seg, 0.3)`）
- 排除 `HIGHLIGHT_SOURCES`
- 过滤 `status === "rejected"`
- 按 `priority` 降序排序取 topActive
- 多个 active edit 的 displayStatus 合并

预计算 Map 必须**完整复刻**这套语义，否则会引入"标记显示错误"回归。当前实现按 `[segments, edits]` 变化统一重建 Map，复杂度为一次性 `O(N×E + Σ relatedEdits log relatedEdits)`；它不再发生在播放帧主路径。若未来需要进一步优化重建，再引入区间索引。

#### 约束 5：双链路必须共享实现

抽 `useEditedPlayback()` composable（或纯函数 + 单 controller），覆盖：
- deleteRanges 规范化（约束 1）
- checkSkip 二分 + 游标
- seek 状态机（约束 2）
- RAF 启停（统一由 `@play` / `@pause` 控制，**PreviewPlayer 必须移除无条件 startRaf**）

WorkspacePage 和 PreviewPlayer 都改为调用这个 composable，避免代码重复和"修一边漏另一边"。

#### 约束 6：wholesale 替换的修复必须用真实 trace 验证

不要预先假设 diff 更新就是答案。先用主路径优化（热点 1/2/3/4/9）后的版本跑一次完整 Performance trace，确认 wholesale 替换仍是可见瓶颈，再决定：
- 选项 A：后端返回 diff（仅新增 segments + edits），前端按字段合并 — 改动大但彻底
- 选项 B：`shallowRef` + 配套 `triggerRef` — 改动小但有心智负担
- 选项 C：保持现状，主路径优化后已经够好 — 零改动

### 4.7 性能指标体系（v2 新增）

v1 只写了"RAF 平均 < 8ms"，证据严重不足。完整指标体系如下。

#### 必须采集的指标

| 指标 | 目标值 | 采集方式 |
|------|--------|---------|
| **RAF 单帧 p50 / p95 / p99 耗时** | p50 < 4ms, p95 < 8ms, p99 < 16ms | `performance.mark('raf-start')` + `measure('raf-duration')` |
| **long task 数量 / 最长阻塞时长** | 30 分钟播放内 long task < 10 次，最长阻塞 < 50ms | `PerformanceObserver({ entryTypes: ['longtask'] })` |
| **程序跳剪 seek 次数** | 单次 normalized range 最多 1 次程序 seek；不统计用户主动 seek | 在 controller 发起程序 seek 时累加，每 10s 上报 |
| **跳剪正确性** | 每个 normalized delete range 最多触发一次程序 seek；不重复命中同一区间；用户 seek 后最终落在 keep range | 分别统计 normalized range、programmatic skip seek 与稳定播放位置 |
| **用户 seek 到稳定播放的延迟** | < 200ms（用户感知"立即响应"）| measure: 从 `seeking` 事件到下一次稳定 RAF |
| **暂停时 RAF 帧数** | 必须为 0（PreviewPlayer 当前 bug 违反此项）| 暂停期间累加 `requestAnimationFrame` 调用数 |
| **Vue flush 耗时 p95** | < 4ms | `app.config.performance = true` 后看 devtools Timeline |

#### 测试方法分层

| 层级 | 工具 | 覆盖范围 | 局限 |
|------|------|---------|------|
| **L1 纯函数** | Vitest `bench` | normalizeDeleteRanges / 二分查找 / 游标 | 无法证明视频事件、Vue flush、浏览器绘制 |
| **L2 组合式** | Vitest + happy-dom | useEditedPlayback 内部状态机 | happy-dom 不是真实浏览器 |
| **L3 浏览器压力** | Playwright + Chrome Performance Timeline | 完整端到端，含视频 / Vue / GC | 需要基准项目数据集 |
| **L4 seek 顺序** | Playwright 单元化测试（mock timeupdate）| 验证 seek 状态机的代际 token、重入屏蔽 | 不覆盖实际视频解码延迟 |

**最低验证标准**: 实施修复时必须同时跑 L1 + L3。L1 给纯函数信心，L3 给浏览器实际表现信心。L4 用于回归 seek 状态机的边界 case。

#### 基准数据集

复用用户项目 `data/projects/20260720-八仙长评`（1167 segments + 989 edits）作为压力测试基准。修复后该项目作为回归基准：每次重大改动后必须在该数据集上跑 L3 浏览器压力测试，对比指标变化。

> **注**: v1 报告里此处误写"1992 edits"，已修正为实际值 989（见附录 A 数据快照）。
