## A: 静音检测清空 AnalysisData（P0 Critical）

### 发现过程

## B: 静音检测不尊重已有 user/LLM 决定（P1 High）

### 发现过程

排查 `add_silence_results` 时发现 `already_covered` 检查使用**精确时间匹配**：

```python
# 错误代码（原 line 680-687）
already_covered = any(
    e.action == "delete"
    and e.status in (EditStatus.CONFIRMED, EditStatus.PENDING, EditStatus.REJECTED)
    and abs(e.start - sil["start"]) < 0.05
    and abs(e.end - sil["end"]) < 0.05
    for e in existing_edits
)
```

User/LLM edits 基于 subtitle segment 范围，与静音检测找到的范围几乎不会精确匹配 → `already_covered` 永远 False → 静音 edit 总被创建。

### 影响机制（前端层面）

`frontend/src/utils/segmentHelpers.ts:resolveSegmentState`：
- 用户对 seg-X 标记 rejected delete (priority=200)
- 静音检测在同范围创建 confirmed delete (priority=100)
- `active = all.filter(e => e.status !== "rejected")` → 过滤掉 user rejected
- `topActive` = silence edit (confirmed delete)
- **UI 显示 "confirmed delete"，用户 reject 决定被完全覆盖**

### 修复

**新增辅助方法** `core/project_service.py:684-728`：

```python
_SILENCE_OVERLAP_SECONDS: float = 0.3  # 与前端 isOverlapping 阈值一致

def _ranges_overlap(self, a_start, a_end, b_start, b_end, min_overlap=0.3) -> bool:
    overlap = min(a_end, b_end) - max(a_start, b_start)
    return overlap > min_overlap

def _has_prior_decision_for_range(self, edits, start, end) -> bool:
    for e in edits:
        if not self._ranges_overlap(e.start, e.end, start, end):
            continue
        if e.source == "silence_detection":
            return True  # 去重
        if e.source == "user":
            return True  # 用户已明确操作（任意 status）
        if e.status in (EditStatus.CONFIRMED, EditStatus.REJECTED):
            return True  # 其他 source 已审核
    return False
```

**修改 add_silence_results** `core/project_service.py:777-801`：

```python
for sil in silences:
    # 始终创建 silence segment（信息层）
    new_segments.append(Segment(...))
    # 仅在无 prior decision 时创建 edit
    if not self._has_prior_decision_for_range(existing_edits, sil["start"], sil["end"]):
        new_edits.append(EditDecision(...))
```

### 历史数据迁移

新增 `_migrate_overlapping_silence_edits` `core/project_service.py:319-366`，在 `open_project` 时调用（line 146）：

- 检测 `source=silence_detection` 且 `status=CONFIRMED` 的 edit

幂等：多次运行无副作用。

## C: LLM 重跑不尊重已有 user edits（P1 High）

### 发现过程

Bug A 修复后，用户询问能否重跑 LLM 智能删除恢复数据。担心"会不会又覆盖掉我的手动操作"。排查 `add_analysis_results` 发现该担忧**完全合理**：

```python
# 错误代码（原 line 1515-1551）
for ar in analysis_results:
    matching_segs = [seg_map[sid] for sid in ar.segment_ids if sid in seg_map]
    if not matching_segs:
        continue
    # 直接创建 EditDecision，无 prior decision 检查
    new_edits.append(EditDecision(
        source=source, status=EditStatus.PENDING, priority=100, ...
    ))
```

### 用户 42 条手动操作的具体风险

| 操作类型 | 数量 | LLM 重跑后果 |
|----------|------|-------------|
| `user rejected delete` | 5 | 若 LLM 建议删除同段 → 新 PENDING edit (priority 100)。前端过滤 rejected 后 LLM 反成 topActive → **"保留"段翻回"待删除"** |
| `user confirmed delete` | 37 | 视觉上 user confirmed (priority 200) 仍胜出，但 SuggestionPanel 多出已审核项 |

### 修复

**修改 add_analysis_results** `core/project_service.py:1521-1537`：

```python
# 预收集已有 user decisions
user_decided_target_ids: set[str] = {
    e.target_id for e in existing_edits
    if e.source == "user" and e.target_id
}

# 循环内检查
for ar in analysis_results:
    matching_segs = [seg_map[sid] for sid in ar.segment_ids if sid in seg_map]
    if not matching_segs:
        continue
    # 任一 segment 有 user edit → 跳过创建 EditDecision
    if any(sid in user_decided_target_ids for sid in ar.segment_ids):
        skipped_due_to_user_edit += 1
        continue
    # ... 正常创建 EditDecision
```

设计决策：
- `AnalysisResult` 本身**仍存入** `analysis.results`（保留 LLM 分析记录，便于审计）
- 仅跳过 `EditDecision` 创建（不产生竞争性建议）
- 多 segment 结果中**任一**有 user edit → 整组跳过（保守策略）

日志增强：
```python
logger.info(
    "Added {} analysis results from {} ({} edits created, {} skipped due to user decisions)",
    len(analysis_results), source, len(new_edits), skipped_due_to_user_edit,
)
```

## 设计反思

### 为什么 Bug A 没有被早发现

1. `AnalysisData(last_run=...)` 的写法看似合理（只是更新时间戳），但 Pydantic 模型的 `results` 字段默认值是 `[]`，不传就清空
2. 单元测试 `test_add_silence_results` 只检查 segments 和 edits，没断言 `analysis.results` 是否保留
3. 集成测试中没有"先 LLM 后 silence"的完整工作流测试

**改进**：本次新增的 `test_silence_does_not_wipe_analysis_results` 锁定了这个回归。

### 为什么 `already_covered` 的精确匹配没被早发现

1. 单元测试 `test_add_silence_results` 用相同的 silence 范围重复运行，触发了 `already_covered`，测试通过
2. 但实际场景中 user/LLM edits 的时间范围与 silence 范围**不同**，`already_covered` 从未触发
3. 没有针对 "已有 user edit 的范围上跑静音检测" 的测试

**改进**：本次新增 6 条 silence-respects-* 测试覆盖各种 prior decision 场景。

### 为什么 Bug C 一直潜伏

1. 历史 LLM 流程是 "先 LLM 后审核"，用户极少有"先操作后重跑 LLM"的场景
2. Bug A 导致用户被迫重跑 LLM，才暴露了 Bug C
3. 没有针对 "user edit 已存在 → 重跑 LLM" 的测试

**改进**：本次新增 4 条 llm-skips-* 测试覆盖。
