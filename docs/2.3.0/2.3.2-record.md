## G3：`toggleEditStatus` 双重 bridge 请求（P1 High）

### 发现过程

`useSegmentEdit.ts:200-225`（修复前）：

```typescript
async function toggleEditStatus(segment, nextStatus?) {
  // ...
  if (state.activeEdit) {
    await call<Project>("update_edit_decision", state.activeEdit.id, status)  // 返回值丢弃
  } else if (state.displayStatus === "rejected") {
    // ...
    await call<Project>("update_edit_decision", rejectedEdit.id, "confirmed") // 返回值丢弃
  } else {
    await call("mark_segments", [segment.id], "delete", "confirmed")         // 返回值丢弃
  }

  const projRes = await call<Project>("get_project")                          // 多余的第二次请求
  if (projRes.success && projRes.data) {
    onProjectUpdate(projRes.data)
  }
}
```

后端契约核对（`core/project_service.py:821-844` 与 `1318+`）：`update_edit_decision` 和 `mark_segments` 均返回 `{"success": True, "data": self._current.model_dump()}` — 第一次写操作**已经返回了完整 Project**，第二次 `get_project()` 完全冗余。

### 修复

`useSegmentEdit.ts:toggleEditStatus` 改为：

1. 捕获第一次写操作的返回值（`writeRes`）
2. **Happy path**：若 `writeRes.success && writeRes.data` 存在，直接 `onProjectUpdate(writeRes.data)` 并 `return`，跳过 `get_project()`
3. **Fallback**：仅在写操作返回数据缺失（旧后端 / 协议不兼容 / 失败）时，才调用 `get_project()` 刷新到权威状态

```typescript
let writeRes = null
if (state.activeEdit) {
  writeRes = await call<Project>("update_edit_decision", state.activeEdit.id, status)
} else if (state.displayStatus === "rejected") {
  // ...
} else {
  writeRes = await call<Project>("mark_segments", [segment.id], "delete", "confirmed")
}

if (writeRes && writeRes.success && writeRes.data) {
  onProjectUpdate(writeRes.data)
  return  // happy path 完成，无第二次请求
}
// 防御性 fallback：刷新权威状态
const projRes = await call<Project>("get_project")
// ...
```

**契约保证**：每次 toggle 在 happy path 只产生 1 次 bridge 写请求（原为 2 次）。

### 阶段 1.1 增强（evaluation-plan §4 阶段 1.1 任务 4-5）

阶段 1 的 G3 修复在功能上正确，但 `writeRes` 类型是手写 `{ success: boolean; data?: Project | null; error?: string }`，且 fallback 失败路径静默返回 `void`。阶段 1.1 做了两点补强：

1. **类型统一**：`writeRes` 改用从 `@/bridge` 导入的 `ApiResponse<Project>`，与 `call<T>()` 返回值一致，消除协议字段漂移风险。

2. **可观察错误路径**：
   - 返回类型由 `Promise<void>` 改为 `Promise<boolean>`：`true` 表示 UI 已成功更新（happy path 或 fallback 刷新成功），`false` 表示完全失败（写操作 + fallback 刷新都失败）。
   - 三态日志：
     - happy path → 不打日志
     - fallback 刷新成功但写失败 → `console.warn` 记录 segmentId + writeError，便于运维定位静默写失败
     - 写 + 刷新都失败 → `console.error` 记录 segmentId + writeError + refreshError
   - 调用方 `WorkspacePage.handleToggleEditStatus` 在 `false` 时通过 `showToast` 弹出用户可见错误。
   - 顺带处理了"resolveSegmentState 报告 rejected 但找不到对应 edit"的不变量违反分支，同样 `console.error`。

## G6：VideoControls delete-range overlay 阻塞 currentTime 更新（P1 High）

### 发现过程

`VideoControls.vue`（修复前）在 progress bar 内 inline 渲染：

```vue
<template v-if="previewMode === 'edited' && deleteRanges?.length">
  <div
    v-for="(range, i) in deleteRanges"
    :key="i"
    class="absolute top-0 h-full bg-red-500/30"
    :style="{
      left: duration > 0 ? (range.start / duration) * 100 + '%' : '0%',
      width: duration > 0 ? ((range.end - range.start) / duration) * 100 + '%' : '0%',
    }"
  />
</template>
```

该 v-for 是 `VideoControls` 模板的一部分。每次 `currentTime` prop 变化（播放时每帧、seek 时、暂停时 timeupdate 事件均会触发），整个 `VideoControls` 重新 render，v-for + 动态 style 表达式也会重新求值。对长项目（如 fix-report.md 引用的 ~971 个 range），每次 currentTime 更新都要执行 971 次 `left`/`width` 字符串拼接。

### 修复

新建 `frontend/src/components/workspace/DeleteRangesOverlay.vue` 纯子组件：

```vue
<script setup lang="ts">
interface DeleteRange { start: number; end: number }
defineProps<{
  ranges: DeleteRange[]
  duration: number
}>()
</script>

<template>
  <div
    v-for="(range, i) in ranges"
    :key="`${range.start}-${range.end}-${i}`"
    class="absolute top-0 h-full bg-red-500/30 pointer-events-none"
    :style="{ /* left/width 计算 */ }"
  />
</template>
```

`VideoControls.vue` 用子组件替换 inline 模板：

```vue
<DeleteRangesOverlay
  v-if="previewMode === 'edited' && deleteRanges && deleteRanges.length > 0"
  :ranges="deleteRanges"
  :duration="duration"
/>
```

**为什么有效**：Vue 的渲染调度机制在子组件 props 引用未变时会跳过该子组件的 render 函数。`deleteRanges` 在 `WorkspacePage.vue:207-212` 是 `computed`，仅在 `edits` 变化时重新计算（toggle / mark 操作），`duration` 是稳定原始值。`currentTime` 变化只触发 `VideoControls` 自身重渲染，不会触发 `DeleteRangesOverlay` 重渲染。

**附加改进**：

- Composite key `${range.start}-${range.end}-${i}` 相比原 index key `i` 能更好识别 range 内容变化（同 `i` 但 start/end 不同时会被识别为新节点），**降低非预期 DOM 复用风险**；但由于 key 仍包含数组索引 `i`，当 range 在数组中位置改变时 key 也会随之改变，**不能严格保证 range 移动时 DOM 节点身份稳定**。鉴于 overlay 是无状态装饰元素，此限制不会立即造成业务错误，但后续若需严格保证移动复用，应先为 delete range 引入稳定 ID 并明确处理重复同起止时间 range 的策略
- 添加 `pointer-events-none` class 防止 overlay 误捕获 progress bar 的鼠标事件

- **render 计数证据**：`does NOT re-render child component when only currentTime changes` —— 用自定义 stub 替换 `DeleteRangesOverlay`，setup/render 函数各计入计数器；currentTime 连续更新后断言 `setupCount === 1 && renderCount === 1`，**直接证明 Vue 跳过了 overlay 的 patch**（而非仅从 prop 稳定性推断）
- **反向证据**：`re-renders child component when deleteRanges actually changes` —— 同一 stub 下 ranges 数组变化时 `renderCount >= 2`，构成 "currentTime 不触发 / ranges 触发" 的完整证据对，排除 "stub 完全未挂载" 的假阳性
- **progress bar 点击**：`emits update:currentTime with proportional value on progress bar click` —— mousedown 触发，断言 emit 比例正确（25/100 × 60s = 15s）
- **非左键忽略**：`ignores non-left-click on progress bar (no seek)` —— button=2（右键）不触发 seek
- **拖动序列**：`emits multiple update:currentTime during drag` —— mousedown(10) → mousemove(50) → mousemove(75) → mouseup → mousemove(90)，断言 emit 包含 6/30/45 且 mouseup 后的 mousemove 不再 emit
- **边界 clamp**：`clamps seek time to [0, duration]` —— 超出右边界 clamp 到 duration、超出左边界 clamp 到 0
- **duration=0 防 NaN**：`clamps to 0 when duration is 0` —— duration≤0 时显式返回 0，不产生 NaN
- **listener 清理**：`removes document mousemove/mouseup listeners after mouseup` —— mouseup 后再 mousemove 不应 emit，证明 listener 已解绑
- **previewMode 切换**：`toggles DeleteRangesOverlay visibility when previewMode switches edited<->original` —— 双向切换 overlay 挂载状态
- **pointer-events 验证**：`overlay does not intercept progress bar clicks` —— 点击落在 overlay 覆盖位置时 progress bar 仍正常 emit seek，验证 `pointer-events-none` 生效

> 注：vue-test-utils 的 `props()` 返回响应式 proxy，破坏了 `toBe` 引用相等断言；改用 `toStrictEqual`。Vue 框架层的 props 引用稳定 ⇒ 跳过子组件 re-render 的契约仍由框架保证。

## 阶段 2：ProjectPatch 局部更新协议

**目标**：把 22 个返回完整 Project 的写方法改造为按层 patch 响应，减少 490 KB 全量序列化与 Vue 级联失效。

**Oracle 咨询后关键决策**：

1. **Schema 形状**：候选 B（按层全量替换），非候选 A（by-id 增量）——Vue Proxy 响应式对层级替换更可预测
2. **Revision 计数器**：内存维护，不进 schema（避免 v1→v2 迁移锁）
3. **Fallback 协议**：内嵌到 `ProjectPatch.full_project` 字段，避免双 API
4. **Undo/Redo 时机**：patch 应用**前**保存完整快照（标准 undo 模式）

**Schema（`core/models.py:ProjectPatch`）**：

```python
class ProjectPatch(BaseModel, frozen=True):
    revision: int                                    # 必填
    timeline_id: str | None = None                   # 默认 active timeline
    segments: list[Segment] | None = None            # None = 未变化
    edits: list[EditDecision] | None = None
    analysis: AnalysisData | None = None
    media: MediaInfo | None = None
    active_timeline_id: str | None = None
    full_project: Project | None = None              # fallback
```

**实施**：

- 后端：5 个高 ROI 方法迁移到 patch envelope（`update_edit_decision` / `update_edit_decisions_batch` / `mark_segments` / `update_segment` / `update_segment_text`）；其余 17 个保留 legacy `{success, data: project.model_dump()}` 响应，前端通过 `isProjectPatch` type guard 自动区分
- 前端：`App.vue:onProjectUpdated` 检测 patch 数据，通过 `lastSeenRevision` 拒绝乱序响应；`applyProjectPatch` 按层替换保持未触碰层引用稳定
- Undo/Redo：`pushSnapshot` 在 patch 应用前保存完整 Project（既有行为，无需改动）

**响应大小对比**：legacy update_edit_decision 响应 ≈ 490 KB；patch envelope（edits-only）≈ 100-150 KB，**节省约 70%** wire payload。

## 阶段 3：排序 invariant 与派生数据优化

**目标**：处理 G4/G5/G13，把"前端每次派生都 re-sort"成本移到"后端写路径保证 invariant"。

**实施**：

- `_enforce_segment_sort_invariant()`：后端私有 helper，stable sort 保证相等 start 时间保留插入顺序
- `update_transcript`：合并 new_subtitles + existing_silence 后显式排序，修复 SRT import 输入乱序的潜在 bug
- `update_segment`：start 变更时调用 invariant helper 并从 active timeline 重新读取 segments 用于 patch payload
- 前端 `mergedSegments`：由 O(S log S) sort 简化为 `() => segments.value` 直通，依赖后端 invariant
- SubtitleOverlay：新增 `seeked` / `timeupdate` 监听，修复 paused 状态下拖动播放头不更新字幕的 bug

**13 条回归测试**（`tests/test_segment_sort_invariant.py`）覆盖 5 个写方法 + 1 条 property-style 混合操作序列。

**buildSegmentStateMap 共享评估**：阶段 2 patch 协议使 props.segments / props.edits 引用稳定后，Timeline.vue 与 SegmentBlocksLayer.vue 各自的 `computed` 自然只在对应层实际变更时重算——显式提升 state map 到父组件的 ROI 过低，跳过重构。
