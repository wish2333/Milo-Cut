## G3：`toggleEditStatus` 双重 bridge 请求（P1 High）

### 发现过程

`useSegmentEdit.ts:200-225`（修复前）：

```typescript
async function toggleEditStatus(segment, nextStatus?) {
  // ...
  if (state.activeEdit) {
    await call<Project>("update_edit_decision", state.activeEdit.id, status)  // 返回值丢弃
  } else if (state.displayStatus === "rejected") {
    // ...
    await call<Project>("update_edit_decision", rejectedEdit.id, "confirmed") // 返回值丢弃
  } else {
    await call("mark_segments", [segment.id], "delete", "confirmed")         // 返回值丢弃
  }

  const projRes = await call<Project>("get_project")                          // 多余的第二次请求
  if (projRes.success && projRes.data) {
    onProjectUpdate(projRes.data)
  }
}
```

后端契约核对（`core/project_service.py:821-844` 与 `1318+`）：`update_edit_decision` 和 `mark_segments` 均返回 `{"success": True, "data": self._current.model_dump()}` — 第一次写操作**已经返回了完整 Project**，第二次 `get_project()` 完全冗余。

### 修复

`useSegmentEdit.ts:toggleEditStatus` 改为：

1. 捕获第一次写操作的返回值（`writeRes`）
2. **Happy path**：若 `writeRes.success && writeRes.data` 存在，直接 `onProjectUpdate(writeRes.data)` 并 `return`，跳过 `get_project()`
3. **Fallback**：仅在写操作返回数据缺失（旧后端 / 协议不兼容 / 失败）时，才调用 `get_project()` 刷新到权威状态

```typescript
let writeRes = null
if (state.activeEdit) {
  writeRes = await call<Project>("update_edit_decision", state.activeEdit.id, status)
} else if (state.displayStatus === "rejected") {
  // ...
} else {
  writeRes = await call<Project>("mark_segments", [segment.id], "delete", "confirmed")
}

if (writeRes && writeRes.success && writeRes.data) {
  onProjectUpdate(writeRes.data)
  return  // happy path 完成，无第二次请求
}
// 防御性 fallback：刷新权威状态
const projRes = await call<Project>("get_project")
// ...
```

**契约保证**：每次 toggle 在 happy path 只产生 1 次 bridge 写请求（原为 2 次）。

### 验证

`useSegmentEdit.test.ts` 的 `describe("toggleEditStatus")` 由原 3 条测试扩展为 7 条，新增 4 条针对 G3 的严格回归断言：


关键回归用例：

- `uses update_edit_decision return value and skips get_project`：断言 `mockCall.mock.calls.map(c => c[0])` 不含 `"get_project"`，且 `update_edit_decision` 仅被调用一次

## G6：VideoControls delete-range overlay 阻塞 currentTime 更新（P1 High）

### 发现过程

`VideoControls.vue`（修复前）在 progress bar 内 inline 渲染：

```vue
<template v-if="previewMode === 'edited' && deleteRanges?.length">
  <div
    v-for="(range, i) in deleteRanges"
    :key="i"
    class="absolute top-0 h-full bg-red-500/30"
    :style="{
      left: duration > 0 ? (range.start / duration) * 100 + '%' : '0%',
      width: duration > 0 ? ((range.end - range.start) / duration) * 100 + '%' : '0%',
    }"
  />
</template>
```

该 v-for 是 `VideoControls` 模板的一部分。每次 `currentTime` prop 变化（播放时每帧、seek 时、暂停时 timeupdate 事件均会触发），整个 `VideoControls` 重新 render，v-for + 动态 style 表达式也会重新求值。对长项目（如 fix-report.md 引用的 ~971 个 range），每次 currentTime 更新都要执行 971 次 `left`/`width` 字符串拼接。

### 修复

新建 `frontend/src/components/workspace/DeleteRangesOverlay.vue` 纯子组件：

```vue
<script setup lang="ts">
interface DeleteRange { start: number; end: number }
defineProps<{
  ranges: DeleteRange[]
  duration: number
}>()
</script>

<template>
  <div
    v-for="(range, i) in ranges"
    :key="`${range.start}-${range.end}-${i}`"
    class="absolute top-0 h-full bg-red-500/30 pointer-events-none"
    :style="{ /* left/width 计算 */ }"
  />
</template>
```

`VideoControls.vue` 用子组件替换 inline 模板：

```vue
<DeleteRangesOverlay
  v-if="previewMode === 'edited' && deleteRanges && deleteRanges.length > 0"
  :ranges="deleteRanges"
  :duration="duration"
/>
```

**为什么有效**：Vue 的渲染调度机制在子组件 props 引用未变时会跳过该子组件的 render 函数。`deleteRanges` 在 `WorkspacePage.vue:207-212` 是 `computed`，仅在 `edits` 变化时重新计算（toggle / mark 操作），`duration` 是稳定原始值。`currentTime` 变化只触发 `VideoControls` 自身重渲染，不会触发 `DeleteRangesOverlay` 重渲染。

**附加改进**：

- Composite key `${range.start}-${range.end}-${i}` 替换原 index key `i`，使 range 在数组中位置变化时仍能复用 DOM 节点
- 添加 `pointer-events-none` class 防止 overlay 误捕获 progress bar 的鼠标事件

### 验证

新建两个测试文件：

```bash
cd frontend && bun run test -- DeleteRangesOverlay VideoControls
# 9 passed (DeleteRangesOverlay 5 + VideoControls 4)
```

`DeleteRangesOverlay.test.ts`（5 条）：

- 渲染数量 = ranges.length
- 空数组渲染 0 个元素
- left/width 百分比计算正确（15-30s / 60s = 25%/25%）
- duration=0 时 left/width clamp 到 0%
- 同一 range 跨渲染 DOM 节点复用（稳定 key 验证）

`VideoControls.test.ts`（4 条）：

- original 模式不挂载
- 空 ranges 不挂载
- **关键**：`currentTime` 连续更新（0 → 25 → 50）后，子组件 props 的 deep equality 保持，证明 currentTime-only 更新不破坏子组件 prop 稳定性

> 注：vue-test-utils 的 `props()` 返回响应式 proxy，破坏了 `toBe` 引用相等断言；改用 `toStrictEqual`。Vue 框架层的 props 引用稳定 ⇒ 跳过子组件 re-render 的契约仍由框架保证。
