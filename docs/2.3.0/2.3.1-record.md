## A: audio-only 项目 OTIO/EDL/XML 导出空文件（P0 Critical）

### 发现过程

用户首次在 audio-only 项目（`.wav`）上点击导出 OTIO / EDL / Premiere XML，发现文件只含骨架（EDL 仅 TITLE/FCM 头、XML 空 sequence、OTIO 空 tracks），接口返回 `success=True` 无错误。但同项目 `export_video` / `export_audio` 正常。

定位到 `core/export_timeline.py:_build_keep_ranges` (line 641)：

```python
# 错误代码（修复前）
return [(s, e) for s, e in keep_ranges if _sec_to_frames(e - s, fps) > 0]
```

其中 `_sec_to_frames(seconds, fps) = int(round(seconds * fps))`。**当 fps=0.0（audio-only 媒体的合法值，由 `ffmpeg_service.py:140-147` 显式设置）时，`seconds * 0.0` 恒为 0**，过滤条件 `0 > 0` 恒为 False，所有 keep ranges 全部被丢弃。

视频导出走的是 `export_service.py:_compute_keep_ranges`（line 681-702），**该函数无 fps 过滤**，所以视频路径正常 — 这就是用户感知"视频导出正常、timeline 导出空文件"的根因。

### 修复

**修复 1（核心防御）** `core/export_timeline.py:640-648`：

```python
# 修复后
if fps > 0:
    return [(s, e) for s, e in keep_ranges if _sec_to_frames(e - s, fps) > 0]
return [(s, e) for s, e in keep_ranges if (e - s) > 0]
```

audio-only 媒体改用时长过滤，不再用帧数过滤。

**修复 2（兜底防御）** 在 `export_edl` / `_build_xmeml_core` / `export_otio` 三处入口加 fps 兜底：

```python
fps = media_info.get("fps", 25.0)
if fps <= 0:
    logger.warning(
        "export_timeline: media_info.fps={} (audio-only?), defaulting to 25.0",
        fps,
    )
    fps = 25.0
```

避免下游 `_seconds_to_timecode(seconds, fps)` 在 `fps=0` 时执行 `total_frames % int(fps)` 触发 `ZeroDivisionError`。

### 验证

新建 `tests/test_export_timeline.py`（9 条测试）：

```bash
uv run pytest tests/test_export_timeline.py -v
# 9 passed
```

关键回归 `test_audio_fps_zero_does_not_drop_ranges` 直接断言 `fps=0.0` 时 keep_ranges 不被清空。

## B: 导出汇总摘要数据错误（P1 High）

### 发现过程

用户点击导出按钮弹出的"导出汇总摘要"对话框显示的裁剪时长 / 占比 / 待删除条数，与工作区右上角徽章 `N edits | -M:S` **数值差近一倍**。

两个数据源用了不同筛选条件：

| 显示位置 | 数据源 | 筛选条件 |
|---------|--------|---------|
| 右上角徽章 (`WorkspacePage.vue:1629`) | 前端 `useExport.ts:confirmedEdits` | `status === "confirmed" && action === "delete"` |
| 弹窗摘要 (`EditSummaryModal.vue`) | 后端 `project_service.py:get_edit_summary` | `action == "delete" and status in (PENDING, CONFIRMED)` |

后端错误地把 PENDING 也算入"已确认删除"。

### 修复

`core/project_service.py:1423-1435`：

```python
# 修复后
confirmed_edits = [
    e for e in edits
    if e.action == "delete" and e.status == EditStatus.CONFIRMED
]
```

### 验证

新增 `test_get_edit_summary_excludes_pending`，覆盖三态：

## C: 导出与标记完全不符（P1 High）

### 发现过程

用户在 edited 跳剪预览模式下看到 subtitle_trim 区间被自动跳过（红色块、自动跳转），但导出后的文件里这些区间**原样保留**。

定位到 `core/project_service.py:generate_subtitle_keep_ranges` (line 2158-2159)：

```python
# 错误代码（修复前）
new_edits.append(EditDecision(
    ...
    source="subtitle_trim",
    status=EditStatus.PENDING,   # <-- 关键
    ...
))
```

subtitle_trim edits 创建时 `status` 固定为 `PENDING`。前端预览（`WorkspacePage.vue:194`、`PreviewPlayer.vue:30`）把 `source === "subtitle_trim"` 当作"隐式 confirmed"跳剪，但后端导出（`export_service.py:435` 和 `export_timeline.py:640`）只看 `status=="confirmed"`，于是全部漏掉。

### 用户决策依据

> subtitle_trim 创建肯定是立即 confirmed 的，也没有别的入口 confirmed，又是快速的工作随时可以删了重新检测的。

subtitle_trim 是用户主动触发的快速工具，`delete_subtitle_trim_edits` 提供一键清除重新生成的入口，语义上等同于"立即生效、可随时撤回"。

### 修复

`core/project_service.py:2153-2183`：

```python
# 修复后
new_edits.append(EditDecision(
    ...
    source="subtitle_trim",
    status=EditStatus.CONFIRMED,   # <-- 立即生效
    ...
))
```

### 验证

新增 `test_generate_subtitle_keep_ranges_creates_confirmed_edits`：
- 断言所有 `source=subtitle_trim` 的 edits 都是 `CONFIRMED`
- 端到端验证：被 `_get_confirmed_deletions` (export_service) 和 `_build_keep_ranges` (export_timeline) 正确识别
- 验证 keep + delete 覆盖完整时间线

新增 `test_subtitle_trim_edits_counted_in_summary`：
- 保证导出弹窗与右上角徽章数字一致（与 Bug B 修复协同）

### 前端冗余清理（未做）

前端 `WorkspacePage.vue:196` 和 `PreviewPlayer.vue:32` 的 `source === "subtitle_trim"` 特判现在已冗余（subtitle_trim 已是 confirmed），但保留无害，留待后续清理。

如后续发现大量用户有此需求，可考虑加一个显式迁移命令。

## 设计反思

### 为什么 Bug A 没有被早发现

1. **首个 audio-only 项目**：之前所有项目都是视频文件（mp4/mkv），fps 始终 > 0
2. **`_build_keep_ranges` 无单元测试**：`grep tests/ test_export_timeline` 返回 0 匹配
3. **`_sec_to_frames(dur, 0)` 的边界行为不直观**：函数返回 `int(round(dur * 0)) = 0`，看似合理实则致命

**改进**：本次新建 `tests/test_export_timeline.py` 锁定 9 个回归场景。

### 为什么 Bug B 一直存在

1. `confirmed_edits` 变量名暗示只含 confirmed，但 filter 包含 PENDING — **命名与实现不一致**
2. `test_get_edit_summary` 调用 `confirm_all_suggestions()` 把所有 pending 转 confirmed，测试**碰巧通过**
3. 没有人对照过前端 `useExport.ts:confirmedEdits` 的 filter 条件

**改进**：本次新增 `test_get_edit_summary_excludes_pending` 显式区分三态。

### 为什么 Bug C 一直潜伏

1. v2.1.1 修复"工作区跳剪体验"时，只在前端 `WorkspacePage.vue` 和 `PreviewPlayer.vue` 加了 `source === "subtitle_trim"` 特判（`docs/2.1.1/audit-report-2.1.1-7.md:159` 记录了"导出过滤条件不应改动"的判断）
2. 当时认为 subtitle_trim 是"自动检测的待定项"，需要用户确认 — 但实际语义是"用户主动触发的快速工具"
3. 没有人对照过前端 `deleteRanges` 和后端 `_get_confirmed_deletions` 的 filter 条件
4. 用户首次在大项目（177 条 subtitle_trim / 636.6s）上对比预览与导出才暴露

**改进**：本次新增 2 条端到端测试，断言 subtitle_trim 被 export_service + export_timeline 正确识别。

## 补充修复（2026-07-20 二次：发布前收尾）

第一阶段合并到 dev-2.3.1 后，发布前又发现并修复两类问题。

### E: WorkspacePage setup 阶段 TDZ 崩溃（P0 阻塞，阻断进入项目页）

**现象**: 用户加载项目后工作区页面完全空白，控制台报：

```
Uncaught (in promise) ReferenceError: Cannot access 'edits' before initialization
    at ComputedRefImpl.fn (WorkspacePage.vue:195)
    at ComputedRefImpl.fn (useEditedPlayback.ts:17)
```

**根因**: `WorkspacePage.vue` 中 `deleteRanges`（line 194）的 computed 引用了 `edits.value`，但 `edits`（line 378）在后面才定义。`useEditedPlayback` 内部的 `watch(playbackRanges, controller.invalidatePendingSeek)` 在 setup 注册时**立即读取一次 playbackRanges 作为初始 oldValue**（Vue watch 默认行为，即便 `immediate:false`），触发链式求值：

```
watch 注册
  → playbackRanges.value 求值
    → deleteRanges.value 求值
      → edits.value   // 此时 edits 处于 TDZ
        → ReferenceError
```

**修复**: 把 `activeTimeline` / `segments` / `edits` 三个 computed 从原 line 374-378 上移到 `deleteRanges` 之前（line 194-205），保留 `duration` / `analysisResults` 原位（无 TDZ 风险）。这是根本修复而非防御性补丁——`useEditedPlayback` 的契约不变，其他调用方（PreviewPlayer）也不受影响。

| 文件 | 改动 |
|------|------|
| `frontend/src/pages/WorkspacePage.vue` | 上移 `activeTimeline` / `segments` / `edits` 三个 computed 到 `deleteRanges` 之前，附 7 行注释解释 TDZ 原因 |

### F: drawSilenceOverlay 全量遍历优化（Bug D 热点 5，MEDIUM）

**现象**: `WaveformCanvas.vue:drawSilenceOverlay` 每次重绘遍历全部 `props.segments`（用户基准项目 1167 段 = 477 subtitle + 690 silence），其中 477 次是无效的 `type !== "silence"` 检查。

**修复**: 预计算 `silenceSegments` computed（按 start 排序的 silence-only 索引），用二分查找定位视口起始位置，循环遇到 `seg.start >= ve` 立即 break。每次重绘从 1167 次比较降到 ~log₂(690) + 可见段数 ≈ 60 次操作。

| 文件 | 改动 |
|------|------|
| `frontend/src/components/waveform/WaveformCanvas.vue` | 新增 `silenceSegments` computed + `findFirstVisibleSilence` 二分函数；`drawSilenceOverlay` 改用二分 + break 早退 |
