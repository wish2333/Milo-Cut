## 1. 当前工作评估

### 1.1 G3：`toggleEditStatus` 单请求

#### 已完成内容

`useSegmentEdit.toggleEditStatus()` 现在保存第一次写操作的返回值：

- `update_edit_decision` 路径直接使用返回的 Project；
- `mark_segments` 路径直接使用返回的 Project；
- 只有返回无 `data` 或失败时才 fallback 到 `get_project()`；
- happy path 不再重复发起第二次完整项目查询。

后端当前契约确实返回完整 Project，因此该修复与现有 API 契约一致。

#### 评估

| 维度 | 结论 |
|---|---|
| 正确性 | 通过；三类主要分支均保留 |
| 性能收益 | 明确减少一次 bridge 往返和一次完整序列化 |
| 兼容性 | 有 fallback，兼容无 data 的旧响应 |
| 测试覆盖 | 已覆盖 happy path、无 data、失败 fallback |
| 残余风险 | fallback 失败时没有向调用方显式返回错误；手写 response 类型可能与 ApiResponse 演进不一致 |

#### 需要补强的点

1. 将 `writeRes` 的手写结构改为复用 `ApiResponse<Project>` 或项目统一响应类型，避免协议字段漂移。
2. 为 fallback 失败增加可观察行为，例如返回 `boolean`、触发 toast，或至少记录明确错误日志；这不是本阶段阻塞项，但应在后续交互可靠性清理中处理。
3. 增加一次真实组件级测试，确认 `onProjectUpdate()` 接收到的是写请求返回值，而不是 fallback 查询结果。

### 1.2 G6：delete-range overlay 拆分

#### 已完成内容

新建 `DeleteRangesOverlay.vue`，`VideoControls.vue` 不再 inline 渲染 delete-range 列表。子组件只接收：

- `ranges`；
- `duration`。

同时增加了：

- edited/original 模式挂载测试；
- 空 ranges 与 duration=0 边界测试；
- 百分比计算测试；
- currentTime 更新后的 props 值稳定测试；
- `pointer-events-none`，避免 overlay 截获 progress bar 鼠标事件。

#### 评估

| 维度 | 结论 |
|---|---|
| 功能正确性 | 通过现有单元与集成测试 |
| 组件边界 | 合理，父组件 API 未改变 |
| 响应式隔离 | 设计上成立：currentTime 不改变 ranges/duration |
| 性能证据 | 不足；测试没有直接统计 child render/update 次数 |
| key 设计 | 有改进，但仍包含数组索引，不能完全保证元素移动时身份稳定 |
| 行为风险 | 需在真实 progress bar 鼠标拖动、点击和切换 previewMode 中补测 |

#### 需要修正的工程表述

当前实现使用：

```vue
:key="`${range.start}-${range.end}-${i}`"
```

这比单独使用 `i` 更能识别 range 内容变化，但由于仍包含 `i`，当 range 在数组中的位置改变时，key 也会改变，不能严格宣称“位置变化时仍能复用 DOM”。由于 overlay 是无状态装饰元素，这不会立即造成业务错误，但实施记录中的表述应改为“降低非预期复用风险”，而不是“保证移动复用”。

后续若要继续优化 key，应先确认 delete range 是否有稳定 ID；若没有，应明确处理重复的同起止时间 range，不能简单移除索引。

## 3. 当前仍存在的主要问题

### P1：G1 wholesale Project 替换链

后端写操作仍普遍返回完整 `Project`，前端仍会整体替换根级 `project`。阶段 1 没有改变这一架构事实。

后续不能只缩小后端响应体；必须让前端按 segment/edit ID 做局部合并，否则响应传输变小但 Vue 级联失效仍然存在。

### P2：文本提交路径仍是单次完整替换

当前文本不是按键提交，因此不存在报告 v1 所说的“每字符调用后端”。但 blur/Enter 或退出全局编辑模式后，仍会触发一次完整项目替换。全局编辑模式关闭时若有多行变更，还可能产生短时间内的多次提交。

该问题应纳入 G1 patch 设计，而不是盲目增加按键级 debounce。

### P1（有条件）：G4/G13 `mergedSegments`

当前前端每次派生 `mergedSegments` 都会复制和排序。可是后端 `update_segment()` 并不保证修改时间后仍按 start 升序。因此下一步必须先建立 service 层排序 invariant 和回归测试，之后才能移除排序。

### P2：G5 与 state map 重复构建

SubtitleOverlay 仍有独立 RAF；Timeline 与 Waveform 仍分别构建 segment state map。它们比 G7 的多次 O(1) Map 查询更值得进入后续 profiling。

## 4. v2.3.2 后续计划

继续使用当前分支 `perf/v2.3.2-stage1-gui-responsive`，不切换到新版本号或新主线。

### 阶段 1.1：收尾与证据补强

**目标**：把已完成的 G3/G6 从“结构性修复”提升到“可审计修复”。

任务：

1. 修正 `2.3.2-record.md` 中关于 composite key 的过强表述。
2. 为 G6 增加 child render/update 计数测试，验证 currentTime-only 更新不会重新执行 overlay render。
3. 增加 progress bar 点击、拖动、previewMode 切换的回归测试。
4. 统一 `ApiResponse` 类型，消除 G3 手写响应类型。
5. 对 G3 fallback 失败增加明确的可观察错误路径。

完成标准：前端测试保持全绿；新增测试不依赖 Vue Test Utils proxy 的假设；报告可以区分“props 稳定”和“render 未发生”。

### 阶段 0：可复现性能基线

**状态**：✅ 已完成（合成 fixture 生成器 + 后端 benchmark；Playwright 端到端 trace 延后到阶段 4 prep）。

虽然工程提交先完成了阶段 1，但后续性能工作必须先补基线：

1. ✅ `tests/fixtures/generate_synthetic_project.py` 生成确定性的 1167 segments / 989 edits fixture（任意 seed 可复现）；
2. ⏸ Playwright 覆盖暂停、seek、右键、文本提交、toggle、播放中操作（延后到阶段 4 prep）；
3. ✅ `tests/perf/backend_benchmark.py` 记录 `Project.model_dump()` / `model_dump_json()` / `update_edit_decision` / `update_segment` / `mark_segments` 耗时；
4. ✅ 输出 p50/p95/p99/max JSON（`tests/perf/results/baseline_stage0.json`），替换报告中的静态估算。

完成标准：✅ 有可重复运行的基准命令和 JSON 基线文件；⏸ Playwright trace 文件待阶段 4 prep 补齐。

**阶段 0 关键结论**（30 runs @ seed=42）：后端 `model_dump()` p50=0.89ms / p95=1.27ms；序列化 Project size=490 KB。**后端不是瓶颈**，GUI 卡顿来源是前端响应式级联（`buildSegmentStateMap()` O(S×E) 与 `project.value = res.data` 全量替换）。详见 [`tests/perf/README.md`](../../tests/perf/README.md)。

### 阶段 2：局部更新协议（仍属于 v2.3.2 设计/实现范围）

**目标**：针对 G1 和文本提交路径，减少完整 Project 替换。

建议顺序：

1. 先定义 `ProjectPatch` schema：变更 segment、edit、timeline 元信息和必要计数；
2. 前端建立 patch merge helper，保留完整 Project fallback；
3. undo/redo 继续保存完整快照；
4. 为文本、时间、edit status 分别实现 patch；
5. 增加 request revision，阻止旧响应覆盖新响应；
6. 在 seek、export、undo、redo、切换 timeline 前 flush pending updates。

完成标准：未修改 segment/edit 的对象引用保持稳定；功能测试覆盖失败回滚和响应乱序；真实 fixture 下比较 patch 前后 trace。

### 阶段 3：排序 invariant 与派生数据

**目标**：处理 G4/G5/G13，并降低重复 O(N×E) 工作。

任务顺序：

1. 为 `add_segment`、`update_segment`、`split_segment`、`merge_segments`、SRT import 补排序测试；
2. 在 service 层统一保证 segment 按 start 升序；
3. 再评估删除 `mergedSegments`；
4. 为 Timeline/Waveform 设计共享 state map 或 edit index；
5. 将 SubtitleOverlay 改为共享 `currentTime`，覆盖 original/edited、播放/暂停和 seeked。

完成标准：排序行为无回归；state map 构建次数和耗时在 trace 中有下降；字幕显示和波形交互不回归。

### 阶段 4：2.3.2 发布收尾

仅在阶段 0–3 完成且性能验收通过后执行：

- 更新 v2.3.2 release metadata；
- 运行前端全套测试、后端全套测试、构建和手动 smoke test；
- 更新 `2.3.2-record.md` 与本评估书的实际数据；
- 生成 release note；
- 在当前 2.3.2 分支完成提交和发布评审。

在此之前不要把 `pyproject.toml` / `frontend/package.json` 的 2.3.1 改成 2.3.2，避免阶段性开发分支被误识别为正式发布版本。

## 6. 风险清单

| 风险 | 说明 | 缓解 |
|---|---|---|
| G6 收益被高估 | props 稳定不等于已测得帧率提升 | 增加 render 计数和 Playwright trace |
