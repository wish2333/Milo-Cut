## 0. Executive Summary

用户报告运行静音检测后，**所有 LLM 智能删除建议与用户手动操作标记全部消失**。经排查发现**三个独立但相关的严重 Bug**，其中 Bug A 直接导致不可逆的数据丢失。

| Bug ID | 名称 | 严重度 | 类型 | 状态 |
|--------|------|--------|------|------|
| **A** | 静音检测清空 AnalysisData | **P0 Critical** | 数据丢失 | **已修复** |
| **B** | 静音检测不尊重已有 user/LLM 决定 | P1 High | 决定覆盖 | **已修复** |
| **C** | LLM 重跑不尊重已有 user edits | P1 High | 决定覆盖 | **已修复** |

**用户实际数据损失**：1 个项目（"20260720-采访陈志远"）丢失 **125 条 LLM 智能删除建议**（消耗 94575 tokens）及其对应的用户审核记录。损失不可恢复（详见 §6）。

## 1. Bug A：静音检测清空 AnalysisData（P0 Critical）

### 1.1 现象

用户运行 LLM 智能删除后获得 125 条建议 → 运行静音检测 → **所有 LLM 建议消失** → 项目保存 → 下次打开时关联的 LLM EditDecisions 也被清理。

### 1.2 根因

`core/project_service.py` 的 `add_silence_results` 方法在更新 timeline 时，错误地用全新的空 `AnalysisData` 替换了原有的 analysis 对象：

```python
# 错误代码（修复前）
self._update_active_timeline(
    transcript=TranscriptData(segments=all_segments),
    edits=all_edits,
    analysis=AnalysisData(last_run=datetime.now().isoformat()),  # BUG!
)
```

`AnalysisData` 模型定义（`core/models.py:285`）：
```python
class AnalysisData(BaseModel, frozen=True):
    last_run: str | None = None
    results: list[AnalysisResult] = Field(default_factory=list)  # 默认空列表
```

构造 `AnalysisData(last_run=...)` 不传 `results` 参数 → `results` 默认为 `[]` → **原 LLM 智能删除、字幕修正、精华提取的所有 AnalysisResult 被清空**。

### 1.3 连锁破坏链（含证据）

从用户项目日志 `data/logs/app_2026-07-20.log` 提取的完整事件时间线：

| 时间 | 事件 | 证据 |
|------|------|------|
| `02:55:47` | LLM 智能删除完成，125 条结果存入 | `Smart-delete analysis done: 125 results, tokens=94575` |
| `02:55:49` | 项目保存（analysis 完整） | `Saved project` |
| **`10:40:04`** | **静音检测运行 → analysis 被清空** | `Added 690 silence segments to project` |
| `10:40:24` | 项目保存（analysis 已空） | `Saved project` |
| `10:41:15` | 重开项目 → `_migrate_highlights` 触发 | `Highlight migration: fixed %d actions, removed %d orphans` |

**第二步连锁破坏**：`_migrate_highlights`（`core/project_service.py:276`）的设计是清理 `analysis_id` 指向不存在 `AnalysisResult` 的 "孤儿" EditDecision。当 Bug A 清空了 `analysis.results` 后，所有 LLM 关联的 EditDecisions 都变成了 "孤儿" → **被 _migrate_highlights 全部删除**。

用户项目当前状态验证：
```
analysis.results count: 0
edits with analysis_id: 0
仅剩 source=silence_detection (690) + source=user (42)
```

### 1.4 严重度评估

- **数据丢失不可逆**：`save_project` 使用 `os.replace(tmp, project_path)` 原子替换，旧文件不进回收站
- **数据/`data/` 在 `.gitignore`** → 无 git 历史
- **无 Windows VSS 快照** → 无系统级还原点
- **日志只记录摘要**（"125 results, tokens=94575"）→ 无原始 LLM 响应内容可恢复
- **task result JSON 仅含 ASR 转写结果** → 不含 LLM 分析输出

**结论：P0 Critical（不可恢复的数据永久丢失）**

### 1.5 修复方案

删除 `add_silence_results` 中对 analysis 的错误替换。静音检测只产生 segments + edits，不应当触碰 analysis 数据。

```python
# 修复后（core/project_service.py:809-815）
# IMPORTANT: do NOT touch analysis data here. Earlier versions did
# `analysis=AnalysisData(last_run=...)` which created a fresh AnalysisData
# with results=[] and wiped all LLM analysis results (smart_delete,
# subtitle_correction, highlight). On next project open, _migrate_highlights
# then removed the now-orphaned edits, destroying AI suggestions.
self._update_active_timeline(
    transcript=TranscriptData(segments=all_segments),
    edits=all_edits,
)
```

### 1.6 回归测试

`test_silence_does_not_wipe_analysis_results`（`tests/test_project_service.py:691`）：
- 预置一个 `AnalysisResult` 到 analysis
- 调用 `add_silence_results`
- 断言 `analysis.results` 长度仍为 1

## 2. Bug B：静音检测不尊重已有 user/LLM 决定（P1 High）

### 2.1 现象

用户对某些 subtitle segments 已经标记了 reject/confirm，但静音检测仍在这些范围创建新的 PENDING delete edit。用户若执行 "confirm all suggestions"，这些静音 edit 变成 CONFIRMED delete，**视觉上覆盖了用户的原决定**。

### 2.2 根因

`add_silence_results` 的 `already_covered` 检查使用**精确时间匹配**（0.05s 容差）：

```python
# 错误代码（修复前，原 line 680-687）
already_covered = any(
    e.action == "delete"
    and e.status in (EditStatus.CONFIRMED, EditStatus.PENDING, EditStatus.REJECTED)
    and abs(e.start - sil["start"]) < 0.05
    and abs(e.end - sil["end"]) < 0.05
    for e in existing_edits
)
```

User/LLM edits 的 `start/end` 通常是基于 subtitle segment 的范围，**与静音检测找到的范围几乎不会精确匹配** → `already_covered` 几乎永远为 False → 静音 edit 总是被创建。

### 2.3 影响机制（前端）

前端 `resolveSegmentState`（`frontend/src/utils/segmentHelpers.ts:23-56`）按如下逻辑合并 edits：

```typescript
const related = edits.filter(e =>
    (e.target_id === seg.id || isOverlapping(e, seg, 0.3))
    && !HIGHLIGHT_SOURCES.has(e.source),
)
const active = all.filter(e => e.status !== "rejected")
const sortedActive = active.sort((a, b) => b.priority - a.priority)
const topActive = sortedActive[0]
```

当 user rejected delete (priority=200) + silence confirmed delete (priority=100) 同时存在：
- `active` 过滤掉 rejected → 只剩 silence edit
- `topActive` = silence edit (confirmed delete)
- UI 显示 **"confirmed delete"** —— **用户的 reject 决定被完全覆盖**

### 2.4 修复方案

新增 `_has_prior_decision_for_range` 方法（`core/project_service.py:697`），基于**时间重叠 > 0.3s**（与前端 `isOverlapping` 阈值一致）判断是否已有决定：

```python
# core/project_service.py:697-728
def _has_prior_decision_for_range(self, edits, start, end) -> bool:
    for e in edits:
        if not self._ranges_overlap(e.start, e.end, start, end):
            continue
        if e.source == "silence_detection":
            return True  # 去重
        if e.source == "user":
            return True  # 用户已明确操作（任意 status）
        if e.status in (EditStatus.CONFIRMED, EditStatus.REJECTED):
            return True  # 用户已审核
    return False
```

调用点（`core/project_service.py:792-796`）：
```python
# 静音 segment 始终创建（信息层），但 edit 仅在无 prior decision 时创建
if not self._has_prior_decision_for_range(existing_edits, sil["start"], sil["end"]):
    new_edits.append(EditDecision(...))
```

### 2.5 历史数据迁移

新增 `_migrate_overlapping_silence_edits`（`core/project_service.py:319`），在 `open_project` 时修复已损坏的项目：

```python
# 检测条件：

# - 与 user edit 时间重叠 > 0.3s

```


## 3. Bug C：LLM 重跑不尊重已有 user edits（P1 High）

### 3.1 现象

用户在 Bug A 修复后想重跑 LLM 智能删除恢复丢失的建议，但担心会覆盖现有的 42 条手动操作。排查后发现该担忧是**合理的**：原 `add_analysis_results` **完全不检查已有 user edits**。

### 3.2 根因

`core/project_service.py:1475` 的 `add_analysis_results` 在循环创建 EditDecision 时，无任何 prior decision 检查：

```python
# 错误代码（修复前）
for ar in analysis_results:
    matching_segs = [seg_map[sid] for sid in ar.segment_ids if sid in seg_map]
    if not matching_segs:
        continue
    # 直接创建 EditDecision，无 prior decision 检查
    new_edits.append(EditDecision(
        source=source, status=EditStatus.PENDING, priority=100, ...
    ))
```

### 3.3 影响场景

用户 42 条手动操作中：

| 操作类型 | 数量 | LLM 重跑后 |
|----------|------|-----------|
| `user rejected delete` | 5 | LLM 若建议删除同段 → 新 PENDING edit (priority 100)。前端 `resolveSegmentState` 过滤掉 user rejected，新 LLM PENDING 反成 topActive → **"保留"段翻回"待删除"** |
| `user confirmed delete` | 37 | LLM 若建议删除同段 → 新 PENDING edit。UI 视觉上 user confirmed (priority 200) 仍胜出，但 SuggestionPanel 多出已审核项 |

### 3.4 修复方案

在 `add_analysis_results` 循环前预先收集 `user_decided_target_ids`，循环中检查跳过：

```python
# core/project_service.py:1521-1527
user_decided_target_ids: set[str] = {
    e.target_id for e in existing_edits
    if e.source == "user" and e.target_id
}

# core/project_service.py:1533-1537（循环内）
if any(sid in user_decided_target_ids for sid in ar.segment_ids):
    skipped_due_to_user_edit += 1
    continue  # 跳过 EditDecision 创建，但 AnalysisResult 仍存储
```

设计权衡：
- `AnalysisResult` 本身仍存入 `analysis.results`（保留 LLM 分析记录）
- 仅跳过 `EditDecision` 创建（不产生竞争性建议）
- 若一个 AnalysisResult 引用多个 segments，**只要任一 segment 有 user edit，整个 result 的 edit 都跳过**（用户已审核过该组的一部分）

### 4.3 保护规则对照表

三处保护遵循统一的"尊重已有决定"原则：

| 场景 | 检查方式 | 触发阻塞的条件 |
|------|---------|---------------|
| 静音检测 vs 现有 edits | 时间重叠 > 0.3s | `source == "silence_detection"` / `source == "user"` / 其他 source 的 confirmed+rejected |
| LLM 分析 vs 现有 edits | segment_ids 集合交集 | `source == "user"`（任意 status）|
| 历史数据迁移 | 时间重叠 > 0.3s | silence confirmed + user rejected delete / user confirmed keep |

## 7. 已知局限

1. **历史 LLM 数据无法恢复**：Bug A 已经造成的数据丢失是不可逆的，本次修复仅保证未来不再发生
2. **迁移阈值与前端一致**：`_migrate_overlapping_silence_edits` 使用 0.3s 重叠阈值，与前端 `resolveSegmentState` 一致。用户项目中 < 0.3s 的小重叠不会被迁移修复（但这些场景前端也不会显示冲突）
3. **segment 级去重 vs 时间级去重**：Bug C 的 LLM 保护基于 `segment_ids` 集合，而非时间范围。如果 LLM 对一个范围给出建议，但用户的 user edit 在另一个相邻 segment 上（不重叠），仍可能创建。这与 LLM 的 segment-targeted 模型一致
